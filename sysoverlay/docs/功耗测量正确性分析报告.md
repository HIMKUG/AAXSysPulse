# SysOverlay-C 功耗测量正确性分析报告

> 分析对象：本仓库 `crates/win/src/msr.rs`、`power_system.rs`、`process.rs`、`crates/win/src/sampler.rs`、`crates/core/src/power.rs`
> 实证数据：本机 `%LOCALAPPDATA%\SysOverlayC\probe.log`（AMD 16 逻辑核，2026-09-09 实测）
> 报告性质：对"功耗显示为什么正确"给出可复算的严格推导，并诚实划定误差边界。

---

## 0. 摘要（结论先行）

"功耗正确"不是一个单一命题，本报告把它分解为**五个可独立论证的性质**：

| # | 性质 | 论证方式 | 结论 |
|---|------|---------|------|
| P1 | **测量段无偏**：能量读数来自硬件计数器，语义正确 | 寄存器语义 + 单位换算复算（§3） | 成立 |
| P2 | **派生段数学正确**：P = ΔE/Δt 可复算、量纲一致 | 用 probe.log 实测数据逐位复算（§4.4） | 成立 |
| P3 | **筛除段只拒异常**：所有拒绝逻辑的上界均高于物理可能值 | 不等式推导（§4.2/4.3） | 成立 |
| P4 | **分摊段守恒且口径一致**：Σ进程瓦 ≤ 整机瓦，与任务管理器同口径 | 求和不等式证明（§5.2） | 成立 |
| P5 | **失败段不伪造**：测不到就显示 `--`/隐藏，绝不输出假 0 | 失败语义设计 + 实测验证（§7） | 成立 |

同时给出诚实的**误差声明**（§9）：分摊模型是一阶近似，存在可界定的系统性偏差；估算项（主板/磁盘）为静态常数；报告末尾明确哪些结论是"被证明的"，哪些是"被界定的"。

## 1. 测量对象与口径定义

在论证"正确"之前必须先定义"正确"的靶子。本实现显示的量是：

```text
整机功耗 Power = CPU实测(RAPL Package + [Intel DRAM 域])
              + GPU实测(厂商模块, EMA 平滑)
              + 内存估算(条数×5W，仅当 DRAM 域不可用时)
              + 主板 44W + 硬盘数×6W
```

- **CPU 部分是测量值**，不是估算——这是整个正确性论证的基石（§3）；
- **GPU/内存/主板/硬盘是估算或混合值**——UI 恒带 `~` 前缀（`fmt_power(.., tilde=true)`），向用户明示口径；
- **进程功耗**是"整机 CPU 实测功率 × 占总算力比例"的归因值（§5），不是独立测量。

因此"正确"的严格含义是：**测量段与硬件语义一致（P1）、派生段数学可复算（P2）、异常被拒绝而非平均（P3）、归因守恒且口径不漂移（P4）、失败可观测（P5）**。

## 2. 链路总览

```text
┌─ 硬件层 ─────────────────────────────────────────────┐
│ WinRing0x64.sys（SCM 服务，需管理员）                  │
│   └─ DeviceIoControl(IOCTL_OLS_READ_MSR) 读 MSR       │
│       AMD: 0xC0010299(单位) + 0xC001029B(PKG能量,64b)  │
│       Intel: 0x606(单位) + 0x611(PKG,32b) + 0x619(DRAM)│
└──────────────┬───────────────────────────────────────┘
               │ 原始计数（单调累加）
┌─ 派生层 ─────▼───────────────────────────────────────┐
│ MsrPower::sample(now_ms)                              │
│   基线差分 → 回绕/倒退分流 → 几何筛(Δraw<2³¹, dt窗口) │
│   → core::power::watts_from_energy_delta             │
│     P = ΔJ×1000/dt_ms ∈ [0, 400]W，否则拒绝并沿用上帧 │
└──────────────┬───────────────────────────────────────┘
               │ 窗口平均瓦数（约 4s 一个有效窗口）
┌─ 合成层 ─────▼──────────────┐  ┌─ 归因层 ───────────┐
│ SystemPower::sample         │  │ NtQuerySystemInfo  │
│  cpu + gpu(EMA) + ram/board │  │  Δ(kernel+user)时间 │
│  /disk → snap.power         │  │  pct = ΔT/(Δt·N)·100│

└─────────────────────────────┘  └────────────────────┘
```

采样节奏（实测）：Power 源独立分频 `power_interval_ms=3000`，采样节拍 ≈2s，故**有效能量窗口 ≈ 4s**（`≥3000ms` 的检查在下一个节拍触发）；进程 CPU% 窗口 ≈ 2s。两者窗口错位的偏差在 §5.3 界定。

## 3. 硬件层：RAPL 能量计数器语义（P1）

### 3.1 RAPL 是什么、为什么可信

RAPL（Running Average Power Limit）是 x86 CPU 内置的**能量计量硬件**：Package 域能量寄存器是一个硬件自增的累计焦耳计数器，由电源管理微控制器按实际功耗持续累加。它不是模型估算——Intel/AMD 官方用它做 Turbo 预算，HWiNFO、LibreHardwareMonitor、scaphandre、Windows 11 的能源估算读的是**同一组寄存器**。因此只要：

1. 寄存器地址选对（§3.2）；
2. 能量单位换算正确（§3.1.1）；
3. 差分窗口处理正确（§4）；

测量值就与硬件真实消耗的能量一致（在 RAPL 硬件自身精度内，Intel 白皮书标称 ±5%~±10%，AMD Zen 未官方标称、实测与插座计量的偏差同量级——这是 P1 的物理边界，见 §9）。

### 3.1.1 能量单位换算：本机实测复算

单位寄存器 `MSR_RAPL_POWER_UNIT` 的 `[12:8]` 位给出能量单位 = `1/2^n` 焦耳。本机 probe.log：

```text
msr unit msr=0xc0010299 raw=0xa1000 n=16 unit_j=0.00001526 dram_ok=0
```

复算：`raw = 0xA1000`，取 `[12:8]` = `(0xA1000 >> 8) & 0x1F = 0x10 = 16`，
故 `unit_j = 1/2^16 = 1.52587890625×10⁻⁵ J ≈ 15.26 µJ/计数` ✓ 与日志一致。
（`dram_ok=0`：本机为 AMD，无可读 DRAM 域，后续合成层据此保留内存条估算——§6。）

### 3.2 域选择：一个曾经真实踩过的错误

**AMD 的 per-core 与 package 寄存器仅差 1**：

| 寄存器 | 地址 | 语义 | 误用后果 |
|---|---|---|---|
| `MSR_AMD_CORE_ENERGY_STATUS` | `0xC001029A` | **每核心**各自计能量 | 读到当前线程所在单核 ≈ 2-3W，整机读数严重偏低 |
| `MSR_AMD_PKG_ENERGY_STATUS` | `0xC001029B` | **整个封装**累计能量 | 正确，实测 47-59W |

早期版本误用 `0xC001029A`，其症状（数值恒在个位数瓦）与"单核功耗"的物理量级吻合，属于**可被物理量级检验捕获的系统性错误**；修正依据是 scaphandre 等开源实现对常量的区分定义，以及修正后数值与负载的相关性恢复（§8）。这个案例反向印证了本报告的检验方法有效：**量级 + 负载相关性**是能量读数的两条物理判据。

Intel 侧使用 `0x611`（PKG）+ `0x619`（DRAM）：PKG 域不含内存控制器，DRAM 域补上才完整，且仅在探测成功时启用（§6 去重逻辑）。

### 3.3 采样线程绑核

`pin_sampling_thread()` 把采样线程一次性绑到 0 号逻辑核。理由：RAPL 是 Package 域全局量，从哪个核读理论上同值；绑核消除每次 `SetThreadAffinityMask`+还原的线程迁移，避免迁移延迟污染墙钟 `dt`（`dt` 直接进入 P=ΔE/Δt 的分母，任何污染都是一次性的功率尖峰）。一次性绑定后每帧零额外系统调用。

## 4. 派生层：P = ΔE/Δt 的严格推导（P2、P3）

### 4.1 定义

功率在物理上不是瞬时量，而是**窗口平均**：

```text
P̄[t₀, t₁] = (E(t₁) − E(t₀)) / (t₁ − t₀)     单位：J / s = W
```

代码中单点实现为 `core::power::watts_from_energy_delta(delta_joules, dt_ms)`：

```text
P = ΔJ × 1000 / dt_ms          （J/ms = kJ/s = W，量纲核对：1000ms/s ✓）
```

展示端与进程分摊端**共用这一个函数**（单一事实源），口径不可能漂移——这是软件工程意义上的正确性保障：不存在"两处公式各改一半"的可能。

### 4.2 三层拒绝条件的推导（每一层都只可能拒绝异常值）

**层 1：窗口长度 `dt ∈ [100ms, 5000ms]`（`MIN_DT_MS`/`MAX_DT_MS`）**

- 下界 100ms：能量计数粒度 δE = `unit_j`。粒度引入的相对误差为
  `ε = δE/ΔE = 1/Δcounts`。以最低负载 10W、最短窗口 100ms 计：
  `ΔE = 1 J → Δcounts ≈ 65 536 → ε ≈ 0.0015%`。窗口越短 ε 越大、且调度抖动使
  `dt` 的相对误差放大（`dt=10ms` 时一次 1ms 抖动 = 10% 误差），100ms 起窗使两类
  误差都压到可忽略。
- 上界 5000ms：正常调度下窗口 ≈ 4s（§2）。超过 5s 只发生在**调度停顿/系统睡眠**
  ——睡眠期间能量计数器停止前进而墙钟（GetTickCount64）继续走，ΔE/Δt 没有物理意义。
  实测日志中两条拒绝恰好都是这类：`dt=25453ms`（25s 停顿）与 `dt=592328ms`
  （≈10 分钟，系统睡眠后恢复）→ 均被窗口上界正确拦截，并沿用上一有效值。

**层 2：几何筛 `Δraw < 2³¹`（`WRAP_LIMIT_RAW`）**

反推其含义（AMD 单位 15.26µJ/count）：`2³¹ counts × 2⁻¹⁶ J = 2¹⁵ J = 32768 J`。
在最大合法窗口 5s 内，它对应的功率下限是 `32768/5 = 6554W`——**比任何消费级 CPU
高两个数量级**。所以：

- 对真实数据该筛恒通过（不误杀）：证明——400W × 5s = 2000J = 1.31×10⁸ counts ≪ 2³¹；
- 对伪数据（虚拟化环境计数器震荡产生的伪跳变）它提供一道与窗口无关的绝对上限。

**层 3：物理钳制 `P ∈ [0, 400W]`（`MAX_CPU_WATTS`）**

400W 的取值论证：桌面/工作站封装功率上限的量级——AMD PPT 出厂上限 ~162-230W、
极限超频 ~280W；Intel PL2 同量级。400W 留有 ~40% 余量，使得：

- 真实读数（哪怕极限超频满载）不可能被误拒；
- 任何 >400W 的"读数"必为异常（计数器伪值、单位换算错误、寄存器误读），直接拒绝。

**关键设计**：拒绝后的行为是 `return self.last_watts`（沿用上一有效值），而不是输出 0 或
`--`。理由：拒绝事件意味着"这一窗口的读数不可信"，而上一有效值是该物理量最近一次的
可信估计——显示 0 会制造"CPU 突然零功耗"的假象，显示 `--` 会把单帧异常放大成整行消失。

### 4.3 回绕/倒退的架构差异化处理

Intel 与 AMD 的计数器宽度不同，**同一策略不可能同时对两者正确**，故分流：

| 架构 | 计数器 | 真回绕形态 | 处理 | 错误模式的拒绝 |
|---|---|---|---|---|
| Intel | 32 位（0x611/0x619） | 计数器到顶回 0，真实 Δ = `cur + 2³² − prev` | `(cur as u32).wrapping_sub(prev as u32)` 还原真实 Δ | 若伪值 > 2³¹，层 2 几何筛拒绝 |
| AMD | 64 位（0xC001029B） | 回绕周期为 2⁶⁴×15.26µJ ≈ **900 万年**，实际不可达 | `checked_sub`：倒退 = 异常，拒绝并沿用上帧 | 虚拟化伪值倒退（实测出现过）被直接拒绝 |

推导 AMD 回绕不可达：`2⁶⁴ counts × 2⁻¹⁶ J = 2⁴⁸ J`；按 100W 恒定功耗需
`2⁴⁸/100 s ≈ 9×10¹² s ≈ 28.5 万年`（即使 400W 也要 7 万年）。因此 AMD 上任何
"变小的读数"都不是回绕，而是异常——把它当回绕还原会算出假功耗，拒绝是唯一正确动作。

### 4.4 基线无条件推进不变量（一个曾被实测抓出的假平均）

`MsrPower::sample` 中 `self.prev = Some((now_ms, pkg, dram))` **无条件执行**，包括被
拒绝的帧。这不是随手写法，而是一条被反例证明的必要不变量：

**反例（若只在有效帧推进基线）**：设计数器震荡（伪值→正常→伪值…），无效帧基线停住，
`dt` 跨越多个震荡周期累积（实测曾达 6s/9s）。此时 `ΔE` 混入伪值差分，
`P = ΔE/Δt` 成了**跨震荡周期的长窗平均**——分母巨大使结果"看起来平滑合理"
（实测输出过连续的 139W），但分子含伪差分，值是假的，且**三层拒绝条件全部失效**
（长窗口让层 1 通过、平均化让层 2/3 的单周期判断失配）。

**不变量的证明力**：基线无条件推进 ⟹ 任何参与计算的窗口 dt ≤ 5s（单周期）⟹ 伪差分
必然以"单周期 ΔE 超限"的形态暴露，被层 2/层 3 逐帧拒绝，而不是被平均稀释。
一句话：**先让异常无处藏身，再谈平均**。

### 4.5 数值复算（用 probe.log 真实数据验证 P2）

取日志相邻两帧（AMD，4s 窗口）：

```text
#025656 msr pkg=20224745406 delta_j=211.5491 dt=4016 watts=52.676575
#025676 msr pkg=20239259362 delta_j=221.4654 dt=4000 watts=55.36635
```

手工复算第二帧：

```text
Δraw   = 20239259362 − 20224745406 = 14 513 956 counts
ΔE     = 14 513 956 × 2⁻¹⁶ J = 14 513 956 / 65 536 = 221.4653 J   （日志 221.4654 ✓，f32 舍入）
P      = 221.4653 J / 4.000 s = 55.3663 W                          （日志 55.36635 ✓）
```

再看 30s 连续片段的计数器单调性：
`20224745406 → 20311036809 → 20398264691 → 20424167696`，严格递增、增量平稳
（每 4s 约 1.3-1.6×10⁸ counts = 200-237J = 50-59W），与"桌面轻负载"物理预期一致。
**P2 成立：读数—换算—差分—除法全链路可手工复算且逐位吻合。**

## 5. 归因层：进程功耗分摊模型（P4）

### 5.1 公式与口径

```text
cpu_pct_i = ΔT_i / (Δt × N) × 100        （占总算力百分比，任务管理器同口径）
W_i       = P_pkg × cpu_pct_i / 100      （share_cpu_power）
```

其中 `ΔT_i` 是进程 i 在窗口内的 Δ(内核+用户) CPU 时间（100ns 单位，来自
`SYSTEM_THREAD_INFORMATION` 的 KernelTime/UserTime 求和），`N` 为逻辑核数，
`P_pkg` 为同一时刻最近的 CPU 实测窗口平均功率。

**口径统一的历史教训**：旧版曾要求"单核归一"的 `[0, N×100]` 口径而调用方实际产出
`[0,100]`，结果分摊整体偏小 N 倍（16 核机差 16 倍）。现在 `share_cpu_power(total_w,
cpu_pct)` 只接受 `[0,100]` 并在注释与类型文档中锁死口径——**单位口径错误是最典型的
"数值看起来对、实际差 N 倍"类 bug，必须用单点函数 + 文档锁死**。

### 5.2 守恒性证明（分摊不会凭空造出能量）

**命题**：对所有进程求和，`Σᵢ Wᵢ ≤ P_pkg`。

**证明**：每个进程在一个窗口内占用的 CPU 时间不超过窗口时长与其可运行核数的乘积，
即 `ΔTᵢ ≤ N·Δt`（单进程最多用满全部 N 核）。于是

```text
Σᵢ pctᵢ = Σᵢ ΔTᵢ/(Δt·N)·100 ≤ (N·Δt)/(Δt·N)·100 = 100
Σᵢ Wᵢ  = P_pkg · Σᵢ pctᵢ/100 ≤ P_pkg · 100/100 = P_pkg   ∎
```

即：**进程功耗列无论显示多少行，加总永远不会超过整机 CPU 实测功率**——分摊是
能量守恒意义上的"切蛋糕"，不是各算各的独立估算。（代码层面的双保险：
`pct.clamp(0,100)` 与 `share = (pct/100).clamp(0,1)`。）

实测验证（probe.log 同一帧）：`total_cpu_w=56.56W`，前六名
`3.15%→1.78W, 1.74%→0.99W, 1.11%→0.63W, 1.07%→0.60W, 0.63%→0.36W, 0.44%→0.25W`。
逐项复算：`56.56 × 3.15% = 1.7817 ≈ 1.78 ✓`；六项之和 = 4.61W = 56.56 × 8.15%，
而六项 pct 之和 = 8.14%（舍入差）✓。**守恒与线性在实测数据上逐位成立。**

### 5.3 模型假设与偏差界定（诚实声明）

"分摊正确"的准确含义是：**在一阶模型假设下守恒、口径一致、量级正确**。已知系统性偏差：

1. **功率 ∝ CPU 时间是一阶近似**。DVFS 使单线程加速比多线程更"贵"（单核高频高压），
   AVX 负载单位时间能耗高于标量负载，内存/uncore 活动不完全随 CPU 时间线性。
   因此 `Wᵢ` 是相对排序与量级正确的估计，不是逐进程的独立测量。这与 Windows 11
   任务管理器的能耗估算思路同级（按活动占比归因硬件实测功率）。
2. **双窗口错位**：`P_pkg` 是 ~4s 窗口平均（§2），`pct` 是 ~2s 窗口。负载在两窗口间
   突变时，`Wᵢ` 瞬时偏高/偏低；其偏差上界为两窗口间 `P_pkg` 的变化量，且在平稳负载下
   两窗口均值收敛一致。选择不强行对齐窗口的理由：进程表 2s 一拉是全系统遍历，
   把它降到 4s 会牺牲 CPU% 实时性——用可界定的瞬态偏差换交互实时性。
3. **空闲底功率的归属**：Package 空载也有底功率（本机负载极轻时仍 ≥47W），一阶模型把
   底功率也按活动占比分摊给了活跃进程。这使得满载进程的分摊值略高于其"净增功耗"。
   若要消除需引入空闲基线扣除，属后续可选项（见 §9）。

### 5.4 历史 31.0W 均一 bug：完整逻辑链（错误的可推导性 ⟹ 修复的可证明性）

**症状**：进程榜功耗列所有进程显示同一个值 31.0W。

**错误链（每一步都可从代码事实推出）**：

```text
① 偏移常量错：OFF_THREAD_COUNT=184 / OFF_THREADS=192
   （x64 SYSTEM_PROCESS_INFORMATION 的 184/192 实为 PagefileUsage/PeakPagefileUsage）
        ↓ 因为
② "线程数"读到页文件用量低 32 位（大数，被 min(1024) 钳到 1024）
        ↓ 且
③ 线程数组基址 = 结构头 + 192 → 指进进程头内部的页文件用量区，
   按 0x50 步长遍历读到的 Σ(Kernel+User) 是垃圾值
        ↓ 因为
④ Δ(垃圾) − Δ(垃圾) 仍为大数 → pct = 大数/(Δt·N)·100 ≫ 100
        ↓ 因为
⑤ pct.clamp(0,100) 把所有进程钳到 100%（钳制本身没错，错的是上游输入）
        ↓ 于是
⑥ W_i = P_pkg × 100/100 = P_pkg = 31.0W，所有进程同值 —— 症状完全复现
```

**修复的正确性论证**：

1. 新偏移表按 x64 结构逐字段累加（含对齐填充）导出：`NumberOfThreads@4`、
   `Threads[]@256(0x100)`、`WorkingSetSize@144`、线程步长 `0x50`、`KernelTime@0`、
   `UserTime@8`。独立旁证：x64 `SYSTEM_THREAD_INFORMATION` 尺寸 = 4×LARGE_INTEGER
   (32B) + StartAddress(8) + CLIENT_ID(16) + Priority(4)+BasePriority(4)
   + ContextSwitches(8) + ThreadState(4)+WaitReason(4) = 80 = 0x50 ✓；
2. **首帧自检**（`proc_offset_check`）：偏移错位会立刻表现为"线程数量级异常 /
   CPU 时间量级异常"，故首帧把前 3 个进程的 (pid, name, cpu100ns, ws) 打进探针。
   实测：`pid=0(Idle, 6.9×10¹¹ 100ns)、pid=4(System)、pid=272(Registry)`——
   System/Registry 是系统固定进程且必须存在，Idle 的累计 CPU 时间量级
   （开机以来的总核时）与 10¹¹~10¹³ 预期吻合 ✓；
3. **症状消解**：修复后 pct 呈现真实的连续分布（0.2%~3.2%），功耗列出现差异化数值
   （0.12W~1.78W），且满足 §5.2 守恒关系——症状链的每一环都被独立证据打断。

## 6. 合成层：整机功耗与去重（双计消除）

```text
Power = cpu(实测) + gpu(EMA) + ram_est + 44W + disks×6W
```

三条去重/对齐逻辑，每条都是防"算两次"或"口径错位"：

1. **内存不双计**：Intel 且 DRAM 域（0x619）可读时，内存功耗已被实测覆盖 →
   `ram_est_w = 0`；DRAM 域不可用（AMD / 驱动未就绪）→ 回落 `条数×5W`。
   关键实现细节：该判定**每帧重评**而非一次性锁存——否则驱动晚一帧就绪会导致
   永久漏算内存项（这一条同样是修过的 bug）。
2. **GPU 窗口语义对齐**：CPU 侧输出的是 4s 窗口平均，GPU 厂商读数若为瞬时值则用
   EMA（`0.6·旧 + 0.4·新`）平滑到同等时间常数，避免整机功耗随帧跳动；
   无 GPU 读数记 0（不是伪造值）。
3. **跨线程单点发布**：`CPU_WATTS_CENTI` 原子量是 CPU 实测瓦数的**唯一**跨线程通道，
   采样线程写、渲染/归因线程读，消除锁与口径分叉。

本机实测合成复算：`52.7(CPU) + 0.0(GPU) + 10(2×5W) + 44(主板) + 24(4×6W) = 130.7W`
✓ 与日志 `syspower total=130.7W` 一致。

## 7. 失败语义（P5：测不到 ≠ 0）

| 失败点 | 行为 | 理由 |
|---|---|---|
| 非管理员 / 无 WinRing0.sys / 服务启动失败 | `ring0()` → None → `sample()` → None → **Power 行整体关闭** | 无测量能力时显示 0 是伪造数据 |
| MSR 单帧读取失败 | 沿用上一有效瓦数（`last_watts`） | 单帧异常 ≠ 物理量消失 |
| 窗口异常/超物理钳制 | 拒绝该帧 + 沿用上帧 + 探针计数 | 见 §4.2/4.3 |
| 进程功耗无整机读数（首帧/驱动缺失） | `power_w = None` → UI 显示 `--` | **`--`（不可测）与 `0W`（测得为零）是两个物理命题**；历史上把 None 退化成 0 正是"所有进程同值"观感的帮凶 |

这一层是"正确性"的最容易被忽视的组成部分：**一个会伪造数据的测量系统，读数再准也不可信**。

## 9. 误差与局限（"正确"的边界）

1. **RAPL 硬件精度**：Intel 标称 ±5~10%，AMD 未官方标称。这是测量原理的上界，
   本实现无法也不需要超越——同源数据之间（历史趋势、进程相对占比）此误差抵消。
2. **归因是一阶模型**：见 §5.3。功率 ∝ CPU 时间的假设在 DVFS/AVX/uncore 活动下有
   系统性偏差，方向可判（单线程重载被低估、内存密集型被低估），量级可界（数十个百分点）。
3. **估算项是常数**：主板 44W、磁盘 6W/块、内存 5W/条为行业经验常数（桌面待机量级），
   不随实际负载变化。UI 以 `~` 前缀披露"混合口径"。
4. **双窗口错位**（4s vs 2s）：瞬态偏差有界、均值收敛，见 §5.3。
5. **CPU_WATTS_CENTI 的 0 哨兵**：存储用 0 表示"无读数"，理论上"恰测得 0.00W"会与
   哨兵混淆——但 Package 空载底功率恒 >0，此路径物理不可达，故接受。

**可选改进**（不影响当前正确性结论）：引入空闲基线扣除提升归因保真度；对齐归因窗口；
GPU 侧接入厂商 SDK 失败时的 NVML/ADLX 双通道。

---

## 10. 结论

功耗显示的正确性由五条独立论证支撑：

- **测量段**（P1）：能量来自 CPU 硬件计数器，寄存器选择、单位换算经实测自检与复算验证；
- **派生段**（P2）：P=ΔE/Δt 单点实现，用真实数据逐位复算吻合；
- **筛除段**（P3）：三层拒绝条件的上界均高于物理可能值，且基线无条件推进不变量
  保证异常只能"逐帧暴露"而不能"被平均稀释"；
- **归因段**（P4）：分摊公式与任务管理器同口径、守恒性有证明、历史 31.0W bug 的
  错误链与修复正确性均有逐环证据；
- **失败段**（P5）：测不到就 `--`/隐藏，永不伪造。

误差边界清晰（硬件精度、一阶归因、常数估算项），并以 `~` 前缀向用户如实披露口径。
**结论：在上述定义与边界内，功耗测量与展示是正确的，且其正确性可以被任何人
按本报告 §4.5/§5.2/§8 的步骤独立复算。**
