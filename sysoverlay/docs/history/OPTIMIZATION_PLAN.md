## 一、功耗采样（最高优先级 —— 直接对应"功耗异常"）

### P0-1 消除 per-read 绑核：这是目前最贵的一笔开销 🔥

**位置**：`msr.rs:205-216`（`read_msr_pinned`）

```rust
let old = SetThreadAffinityMask(cur, 1);   // 强制迁移到 CPU0
let v = read_msr(r, index);
let _ = SetThreadAffinityMask(cur, old);   // 再迁回来
```

`SetThreadAffinityMask` 会**强制线程迁移 + 缓存/TLB 失效**。而 `sample()`
（`msr.rs:257-259`）一次要读两个寄存器：

```rust
let pkg  = read_msr_pinned(r, pkg_idx)?;                        // 绑核×2 + IOCTL×1
let dram = read_msr_pinned(r, MSR_INTEL_DRAM_ENERGY).unwrap_or(0); // 绑核×2 + IOCTL×1
```

**一次功耗采样 = 4 次线程迁移 + 2 次内核调用。** 而且更糟的是：绑核期间采样线程
被强制搬到 CPU0 再搬回来，**它自己测的 wall-clock `dt` 被拉长了**（这正是历史上
"功耗失真/要裁剪 MAX_DT_MS"症状的结构性来源），同时把负载强行堆到 CPU0，
本身就是用户感知到的"CPU 占用异常"。

**方案**：把「绑核」从 per-read 提升为「**线程级一次性**」。
新建一个**专用 MSR 读线程**，启动时 `SetThreadAffinityMask(self, 1)` 常驻 CPU0，
采样线程通过 channel 请求读数。附带收益：采样线程不再被迁移，`dt` 干净。

**收益**：功耗采样内核调用减半，线程迁移从每帧 4 次降到 0 次；整机 CPU 占用与 CPU0 热点同步下降。
**风险**：低。需验证 AMD 多 CCD 下常驻 CPU0 的读数语义仍稳定。

### P0-2 AMD 上不要再去读 Intel 的 DRAM MSR

**位置**：`msr.rs:259`

```rust
let dram = read_msr_pinned(r, MSR_INTEL_DRAM_ENERGY).unwrap_or(0);
```

`MSR_INTEL_DRAM_ENERGY`（0x611）在 AMD 上**必然失败**。但代码每帧都无条件读一次 ——
等于每帧白付「P0-1 里那套绑核 + IOCTL」的全部代价，换来一个恒为 0 的值。
而本机正是 AMD（RX 9070 GRE）。

**方案**：用已有的 `dram_ok` 标志短路，AMD 分支根本不发起调用。

**收益**：AMD 机器上功耗采样开销直接 **减半**，且省掉大量无谓的线程迁移。
**风险**：无。

### P0-3 CPU / GPU 功耗的**时间窗口不一致**（数值跳变的根因之一）

**位置**：`power_system.rs:90-95` vs `msr.rs`

整机功耗是 `CPU + GPU + 静态项` 三者相加，但三者的口径不同：

| 项 | 窗口 | 性质 |
|---|---|---|
| CPU | 3s 差分平均（`power_interval_ms=3000`） | 窗口平均 |
| GPU | vendor 瞬时读数（随 `plan.gpu` 每 ~2s 取一次） | **瞬时值** |
| 静态项 | 常量 | 常量 |

平均窗口的值和瞬时值相加，结果会随 GPU 瞬时抖动上下跳 —— 这就是"功耗异常"里
最容易被误判成"读数不准"的那一类。

**方案**：把 GPU watts 也做**同窗口平均**（与 CPU 对齐的 EMA 或窗口均值），
相加前保证二者时间口径一致。

**收益**：功耗读数稳定性显著提升，不再无故跳变。
**风险**：低。窗口长度需在"跟手"与"平滑"间取舍，建议先取 3s。

### P0-4 DRAM 去重是**单向不可逆**的

**位置**：`power_system.rs:86-88`

```rust
if self.ram_est_w > 0.0 && self.msr.dram_available() {
    self.ram_est_w = 0.0;   // 一旦置 0 就再也回不来
}
```

这是 latch 不是求值：如果 DRAM 域后续失效（驱动重载、休眠恢复），
估算项不会恢复，整机功耗会**静默偏低**。

**方案**：每帧重新判定 `ram_est_w = if dram_available { 0 } else { sticks * 5 }`。

**收益**：消除休眠/驱动重载后的隐蔽偏低的功耗读数。
**风险**：无。

### P0-5 静态估算项是硬编码的魔法数

**位置**：`power_system.rs:17-19`

```rust
const EST_RAM_W_PER_STICK: f32 = 5.0;
const EST_MAINBOARD_W:   f32 = 44.0;
const EST_DISK_W:        f32 = 6.0;
```

DDR4 与 DDR5 单条功耗差近一倍；NVMe 与机械盘也完全不同。

**方案**：改为 `Config` 可配置项；默认值按 SMBIOS 内存类型（`sysinfo.rs` 已有
Type 17 解析能力）与磁盘类型选取。

**收益**：估算误差收敛，且用户可自行校准。
**风险**：低（配置已有兼容解析框架）。

## 二、渲染开销

### P1-6 脏矩形增量上屏

**位置**：`gdi.rs:298`（`update_layered`）

当前每次内容变化都把整块画布提交给 `UpdateLayeredWindow`。但通常只有一两个
数值变了，绝大多数像素与上一帧完全相同。

**方案**：改用 `UpdateLayeredWindowIndirect`（原生支持 `prcDirty`），
让 renderer 返回脏矩形并集（多个脏区取 bounding box 即可，先简单后精细）。

**收益**：上屏带宽与 GDI 合成开销大幅下降，尤其高 DPI 大窗口。
**风险**：中。`prcDirty` 语义需仔细处理，滤镜/alpha 场景要回归验证。

### P1-7 字形 Atlas（把逐像素算法换成 memcpy）

**位置**：`ui/src/font.rs`（715 行点阵字体 + 浮点放大）

当前每帧对每个字符做多次浮点缩放采样与 alpha 混合。而字符×缩放档的组合
其实是有限的（字号档位固定）。

**方案**：启动时把「字符 × 缩放档」预烘焙成一张 atlas 位图，绘制时按行 `memcpy`
/固定合成，彻底消灭逐像素浮点运算。

**收益**：文字绘制（软件渲染最大热点）接近纯内存带宽受限。
**风险**：中。atlas 内存占用需按档位估算；`render_mode=Eco` 可只用一两档。

### P1-8 画布改为脏矩形局部清零

**位置**：`offscreen.rs:49` —— `resize()` 每帧 `self.pixels.fill(0)` 清空整块画布。

**方案**：配合 P1-6，只清实际重绘区域；并对未变化区域跳过绘制。

**收益**：每帧省一次全画布 memset（典型 187KB 量级）。
**风险**：低。需要与脏矩形机制同步推进。

### P1-9 静态层缓存：背景/圆角/阴影只画一次

**位置**：`ui/src/renderer.rs`（`decor` / `fill_round_rect`）

背景板、圆角、阴影只随 `cfg` 变化，与每帧的数值无关，却被逐帧重算
（`offscreen.rs:209 fill_round_rect` 含逐像素圆角判定）。

**方案**：把"装饰层"单独缓存成一张图，`cfg` 未变时直接 blit，动态层只合成文字。

**收益**：消除每帧的圆角/阴影计算。
**风险**：中。需要拆分渲染管线的静态/动态两个阶段。

### P1-10 取消每帧 `GetWindowRect`

**位置**：`gdi.rs:141`

每帧一次用户态/内核态切换去拿窗口尺寸，而尺寸只在 `WM_SIZE` / `WM_DISPLAYCHANGE`
才变。

**方案**：把尺寸缓存在 `ThreadState`，由上述消息失效。

**收益**：每帧省一次系统调用；量小但零风险。
**风险**：无。

### P1-11 数值字符串零堆分配

每帧用 `format!("{:.1}", v)` 产生 `String`（堆分配 + 释放）。

**方案**：写栈缓冲（`[u8; 16]` + 手写整数/小数格式化），或直接 Arc 化共享。

**收益**：消灭每秒数十次的堆分配，降低分配器抖动。
**风险**：低。注意宽度不足时的截断语义。

### P1-12 按指标独立脏判定

CPU 每 100ms 变一次，而 GPU/Net/Power 的分频是 1~3s。当前任一变化都整帧重画。

**方案**：把帧哈希**按行/按指标拆分**，只让变化的那一行走绘制路径。

**收益**：CPU 高频刷新时，其余静态行零重绘。
**风险**：中。需要 renderer 支持分区绘制。

## 三、采样 / CPU 占用

### P0-13 消灭每帧 256KB 分配

**位置**：`process.rs:158-173`

```rust
let mut size: u32 = 256 * 1024;
let mut buf: Vec<u8> = vec![0u8; size as usize];  // 每帧：分配 + 清零 256KB
...
buf = vec![0u8; need];                            // 失败重试：再来一次
```

每次进程采样都要「分配 + memset 256KB + 释放」，扩容时再来一轮。

**方案**：把 `buf` 提升为采集器成员 / 线程局部 **`Vec` 复用**，容量只增不减；
并把上一帧实际 `size` 作为下一次的起始值，规避重试放大。

**收益**：进程榜每次采样省掉数百 KB 级的分配与清零。
**风险**：无。

### P1-14 HashMap 双缓冲复用

**位置**：`process.rs:114` —— `HashMap::with_capacity(rows.len())` 每帧新建并丢弃。

**方案**：两个 map 交替 `clear()` / `swap()`，保留已分配桶。

**收益**：省掉每帧的哈希表分配与再散列。
**风险**：无。

### P1-15 probe 日志惰性化（**已确证的真实浪费**）

**位置**：`probe.rs` 的 `pub fn log(line: &str)` —— 它接收**已经格式化好的**字符串。

于是所有调用点例如 `main.rs:326`：

```rust
probe::log(&format!("cycle cost_ms={} sleep_ms={} ...", cost_ms, sleep_ms, ...));
```

都是**先 `format!`（堆分配）再进函数，函数内部才 `if !enabled() { return }`**。
也就是说：**调试日志关着的时候，每帧照样付出一次堆分配和格式化开销。**

**方案**：增加惰性接口 `log_lazy(|| format!(...))` 或 `log_fmt!` 宏，
把 `enabled()` 判断提到 `format!` 之前；把采样主循环等热路径调用点全部切过去。

**收益**：默认（非调试）运行下省掉每帧一次字符串分配。**已验证，确定性收益。**
**风险**：无。

### P1-16 GPU 利用率与功耗分频

**位置**：`sampler.rs:102` —— `gpu_vendor::sample()` 同时返回 util 与 watts。

watts 服务于功耗显示（3s 口径），却跟着 util 的频率走。

**方案**：watts 与 `power_interval_ms` 对齐，util 维持现频率。

**收益**：减少跨驱动（NVML/ADL/IGCL）调用次数。
**风险**：低。

### P2-17 网卡枚举降频

**位置**：`proc_net.rs:95,130` —— 每次采样 `GetIfTable2` + `FreeMibTable`（内核分配整表）。

网卡**名单**基本不变，变的是字节计数。

**方案**：名单/索引映射每 60s 刷新一次，其间复用缓存的接口索引。

**收益**：降低 iphlpapi 调用频率。
**风险**：中。需处理网卡热插拔与虚拟网卡变动。

### P2-18 采样线程优先级降级

把采样线程设为 `THREAD_PRIORITY_BELOW_NORMAL`，避免与前台争抢。

**收益**：前台/游戏场景更平滑，符合"监控器不该抢资源"的原则。
**风险**：低。注意别影响 `dt` 精度（此线程已改由 P0-1 的专用线程读数）。

### P2-19 进程榜不可见时彻底停采

已有部分逻辑，需确认 `query_all()`（含 Nt 大查询）在窗口不可见时**确实不被调用**，
否则隐藏后仍在付 256KB Nt 查询的代价。

**收益**：隐藏状态下采样开销归零。
**风险**：低。**建议先用探针确认再决定是否动。**

### P2-20 合并每帧冗余系统调用

**位置**：`window.rs:472-484`（`WM_NEW_SNAPSHOT` 分支）

该分支里 `get_state_ptr(hwnd).as_ref()` 被调两次，`IsWindowVisible` 与
`GetWindowRect` 各一次 —— 这些结果在同一帧内是恒定的。

**方案**：合并为一次取状态 + 缓存可见性/尺寸（与 P1-10 联动）。

**收益**：每帧省 2~3 次系统调用。
**风险**：无。

## 四、建议实施顺序

先做**确定性、低风险、立刻见效**的，把-noise 打掉，再动结构：

1. **第一批（半天）**：P0-2 → P0-15 → P0-13 → P0-4 → P0-5
   —— 全是"删除浪费"和"修正逻辑"，几乎无回归风险，且 P0-2/P0-15 收益确定。
2. **第二批（1~2 天）**：P0-1（专用读线程）→ P0-3（窗口对齐）→ P1-14 → P1-10 → P2-20
   —— P0-1 收益最大但需要线程结构调整。
3. **第三批（结构改造）**：P1-6 → P1-8 → P1-7 → P1-9 → P1-12 → P1-11
   —— 脏矩形 + 字形 atlas + 静态层缓存，改造量最大，**务必逐项验证视觉效果**。
4. **第四批（锦上添花）**：P1-16 → P2-17 → P2-18 → P2-19

> 每批之间请各抓一轮 perf 数据对比 —— 老规矩：**先测量，再优化，最后才结论**。
