> 证据来源：用户截图（2026-09-12 22:39:33，游戏运行中）+ 本机实时 probe 日志 `%LOCALAPPDATA%\SysOverlayC\sysoverlay_20260912_2232.log`

> 用户裁决（本次改动依据）：**"只要功耗开着就要采集到完整数据；GPU 关掉只是不采样占用率，功耗仍要采。"**

## 0. 结论先行

| 项 | 内容 |
|---|---|
| **现象** | 悬浮条功耗格显示 `164W`；同屏硬件监控（游戏加加）读数：CPU 功耗 62.8W、GPU 功耗 239W。**整机功耗低于其中任一单项的分量关系明显不成立**（同期 GPU 单项 239W > 总功耗 164W）。 |
| **根因（唯一）** | 整机功耗的 GPU 分量来自 `gpu_vendor::sample()`，而**该调用只在 `plan.gpu` 为真时发生**。用户当前配置 `show_gpu=0`（3 格布局：时间 / 网速 / 功耗）→ 厂商后端从未初始化 → `gpu_watts = None` → 合成时该项按 `0.0` 计入。 |
| **性质** | **设计耦合缺陷**，不是传感器不可用。用户最常见的用法（极简 3 格、只留网速+功耗）**必然**触发，属默认路径而非边界情形。 |
| **量级** | `164.1 = 86.1(CPU) + 0.0(GPU) + 10(内存) + 44(主板) + 24(4×硬盘)`，缺失项 = 显卡板功率 239W → 整机功耗**低估约 60%**（实际应约 ~400W）。 |
| **次生缺陷** | ① GPU 行由开→关时，`SystemPower.gpu_watts` 不清零 → 整机功耗**冻结在最后一次显卡读数**（陈旧值，不归零也不更新）；② 估算标注 `~` 从未生效（唯一调用点硬编码 `estimated=false`），混合口径（44W 主板 + 内存 + 硬盘常数，且 GPU 可能缺项）冒充实测值；③ `power_display` 是死配置（解析/落盘但无人读取）。 |
| **修复** | 采样门 `plan.gpu` → `plan.gpu \|\| plan.power`（GPU 行关只意味着不显示占用率，不意味着不测功耗）；厂商库改为"两行都关才卸载"；新增缺项状态翻转探针。详见 §3。 |

## 2. 根因（代码级）

### 2.1 唯一调用点被 GPU 行开关门控

`crates/win/src/sampler.rs:136-157`

```rust
if plan.gpu {                                   // ← 门控：GPU 行开关
    let t = crate::perf::begin();
    let (v_util, v_watts) = gpu_vendor::sample();   // ← GPU 功耗的唯一来源
    self.syspower.set_gpu_watts(v_watts);           // :139
    ...
} else {
    self.push_diag(SamplerId::Gpu, SampleOutcome::Skipped, 0);   // ← 什么都不做
}
```

`gpu_vendor::sample()` 是全仓库对 `SystemPower::set_gpu_watts()` 的**唯一**写入点（grep 确认）。GPU 行关闭 ⟹ `gpu_watts` 永远停在 `None`。

### 2.2 合成段把"缺项"折成 0 并静默显示

`crates/win/src/power_system.rs:104-116`

```rust
let gpu = if let Some(w) = self.gpu_watts { ...ema... } else {
    self.gpu_watts_ema = None;
    0.0                          // ← None 降级成 0，并入总和
};
let total = cpu + gpu + self.ram_est_w + EST_MAINBOARD_W + self.disks as f32 * EST_DISK_W;
```

`power_system.rs:10` 的文档把"GPU 功耗拿不到 → 记 0 继续显示"定义为可接受的降级。**降级本身没错，错的是它的触发条件是"另一个功能的行开关"，与传感器能力无关。**

### 2.3 开关不对称：功耗行有独立查询门，GPU 侧没有等价物

`crates/win/src/window.rs:159-169`

```rust
let power_gate = cfg.power_enabled && cfg.power_query;   // 功耗行有独立"功耗查询"门
let mask = (cfg.show_cpu as u32) | ((cfg.show_mem as u32) << 1) | ((cfg.show_gpu as u32) << 2)
         | ((cfg.show_net as u32) << 3) | ((power_gate as u32) << 4);
```

功耗行被专门设计成"显示"与"采集"两开关（`power_enabled` / `power_query`），说明设计者已经意识到"显示开关不该决定采集"；但 GPU 功耗分量**恰恰**被显示开关决定 —— 同一份设计原则没有贯彻到 GPU 侧。

### 2.4 次生缺陷 A：GPU 行中途关闭 → 陈旧值冻结

`crates/win/src/sampler.rs:84-89`

```rust
if prev[2] && !cur[2] {
    crate::gpu_vendor::teardown();          // 清的是 gpu_vendor 内部的原子缓存
    crate::proc_gpu::invalidate_topology();
}                                           // ← 没有 self.syspower.set_gpu_watts(None)
```

`gpu_vendor::teardown()` 只清 `GPU_WATTS` 原子，**不触碰** `SystemPower.gpu_watts`。因此运行中把 GPU 行关掉、功耗行保持开启时，整机功耗会**永久沿用关闭瞬间的显卡读数**（既不更新也不归零）——与本次"启动即 0"是同一耦合缺陷的另一个面。

### 2.5 次生缺陷 B：`~` 估算标注从未生效

`crates/ui/src/renderer.rs:609`

```rust
// 整机功耗 = 实测(CPU/GPU) + 估算(内存/主板/硬盘)
fmt_power(&mut b, v, false);        // ← 硬编码 false
```

`crates/core/src/units.rs:243` 的 `fmt_power(.., estimated)` 已实现 `~` 前缀，但唯一调用点恒传 `false` ⟹ `~` 在生产路径上不可达。而 `功耗测量正确性分析报告.md` §1/P5 明确承诺"GPU/内存/主板/硬盘是估算或混合值——UI 恒带 `~` 前缀"。**文档承诺与代码实现不一致**：一个恒含 44W 主板常数 + 内存/硬盘常数、且可能缺 GPU 项的数值，以 `164W` 这种"精确到个位"的形态呈现，属于过度声称精度。

## 3. 修复实现（已落地）

### A. 解耦采样门（主症状）—— `crates/win/src/sampler.rs`

采样门由 `plan.gpu` 放宽为 **`plan.gpu || plan.power`**：功耗行开着就一定要拿到显卡实测瓦数；只有 GPU 行关闭时，才不回写 `snap.gpu`、不跑 D3DKMT 兜底（省约 74ms）。瓦数始终无条件发布给 `SystemPower`。

```rust
// ⚠️ 采样门 = GPU 行 ∨ 功耗行（用户拍板：功耗开着就要拿到完整数据）。
// 「GPU 行关」只代表不显示占用率，不能连显卡瓦数一起停掉。
if plan.gpu || plan.power {
    let t = crate::perf::begin();
    let (v_util, v_watts) = gpu_vendor::sample();
    self.syspower.set_gpu_watts(v_watts);   // 瓦数无条件发布
    if plan.gpu { /* 原逻辑：vendor 优先 → 缓存 → D3DKMT 兜底，回写 snap.gpu */ }
    else        { /* 功耗行专供：只要瓦数，不要占用率 */ }
} else {
    self.push_diag(SamplerId::Gpu, SampleOutcome::Skipped, 0);
}
```

### B. 两行都关才卸载厂商后端 —— `crates/win/src/sampler.rs::on_schedule_change`

```rust
// Power 行关：
if prev[4] && !cur[4] {
    crate::msr::teardown();
    // ...（原有：清 CPU 瓦数、复位退避、记诊断）
    if !cur[2] {                                   // GPU 行也关着 → 厂商库已无使用者
        crate::gpu_vendor::teardown();
        self.syspower.set_gpu_watts(None);
    }
}
// GPU 行关：
if prev[2] && !cur[2] {
    if !cur[4] {                                   // 功耗行也关 → 才真卸载
        crate::gpu_vendor::teardown();
        self.syspower.set_gpu_watts(None);         // 后端没了 → 清陈旧瓦数
    }
    crate::proc_gpu::invalidate_topology();
}
```

配套：`settings/mod.rs` 的 GPU 行关闭提示（"厂商功耗读数需重启应用恢复"）改为**仅在功耗行也关时**弹出，否则那句话不成立。

> 副产品（正面）：GPU 行 开→关→开 的往返不再需要重启——厂商库在功耗行开着时始终存活，占用率随开关即时恢复。

### C. 缺项可观测 —— `crates/win/src/power_system.rs`

```rust
// GPU 瓦数缺失时整机功耗会静默漏掉整个显卡项（BUG-4 的成因），
// 故在状态**翻转**时记一行探针（不每帧刷屏）。
let missing = self.gpu_watts.is_none();
if missing != self.gpu_watts_missing {
    self.gpu_watts_missing = missing;
    probe::log(if missing {
        "syspower gpu watts unavailable → 显卡项按 0 并入（整机功耗偏低，查 gpu_vendor 读数）"
    } else {
        "syspower gpu watts available → 显卡项已纳入整机功耗"
    });
}
```

## 5. 关于 CPU 读数差异的判定方法（留待用户同窗口比对的结论）

已知事实足以**排除**本实现 CPU 侧的系统性错误：单位换算 `n=16 → 15.26µJ/count` 正确、计数器严格单调、`dt=3000ms` 落在 `[100,5000]` 合法窗内、全会话零拒绝。故差异只可能来自口径：

1. **窗口**：本实现是 3s 窗口平均（`power_interval_ms=3000`），若对方显示瞬时值，游戏负载抖动下可以差出数十个百分点；
2. **域**：AMD RAPL PKG 含 IOD/SoC，若对方读的是 core 域或做了空闲基线扣除，会系统性偏低。

定性方法（一次即可）：开启 GPU 行后，在同一时刻分别记录 probe 日志的 `msr pkg=... watts=` 与监控软件的 CPU 功耗读数，各取 10 个采样点做配对比较；若两者**均值差在 10% 内**，则差异纯粹来自窗口抖动，本实现无偏；若稳定偏低 20%+ 且方向一致，再立项查域定义。

## 6. 验收标准

1. **主症状**：配置 `show_gpu=0 / power=1`（即当前 3 格布局）下，probe.log 出现 `adl backend ready ...` 与 `adl pmlog sensors ...`；`syspower` 行的 `gpu=` 非零，且 `total == cpu + gpu + ram_est + 44 + disks*6` 逐位可复算；
2. **对账**：游戏运行中，整机功耗 ≈ 本实现 CPU + 显卡板功率（与游戏加加 GPU 功耗对账，差值落在常数估算项 + 窗口抖动内），不再出现"总功耗 < GPU 单项"；
3. **冻结值**：运行中把 GPU 行由开切关、功耗行保持开启 → 下一轮功耗刷新的 `gpu=` 反映**当前**显卡功耗（不冻结在切换瞬间的值）；再把功耗行也关 → probe 出现 `gpu watts unavailable`、厂商库卸载；
4. **口径标注**：本次未改（见 §3-D），`~` 前缀仍待口径决策；
5. **回归**：GPU 行开启时利用率行为不变（vendor 优先 + 缓存 + D3DKMT 兜底）；`cargo check --workspace` 零警告、`cargo test --workspace --lib` 72 项全绿（已通过）。

## 7. 一句话总结

功耗数值本身没有算错——**是输入少了一项**：整机功耗的 GPU 分量被"GPU 行开关"劫持，关掉 GPU 行的极简布局必然把显卡功耗（本次 239W，占实际整机约 60%）算成 0；叠加 `~` 标注失效，用户看到的是一个"精确"但系统性偏低的数字。**修复已落地**：采样门放宽为 `plan.gpu || plan.power`（GPU 行关只停占用率、不停功耗），厂商库改为两行都关才卸载，并加了缺项状态探针；release 已重建落盘 `dist/sysoverlay-app.exe`。
