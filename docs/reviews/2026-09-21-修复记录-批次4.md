## 1. P1-22 跨进程契约单一真源：`core::contract`

- **症状**：两个进程只靠"磁盘 INI + Win32 消息"对齐，而这套约定的字面量在两侧各写一遍：窗口类名 4 份、`WM_*` 消息号 3 份、程序/驱动/服务/注册表/目录 名 十余处、`CONFIG_VERSION` 主程序侧 `config.rs` 定义而引导侧写死 `version: 3`。
- **根因**：没有共同的真源模块。报告原话是"改一端即失联"，且**没有任何编译期或运行期手段能发现**——这类漂移全部表现为"静默无反应"。
- **如何修正**：新建 `sysoverlay/crates/core/src/contract.rs`（`core/src/lib.rs` 里 `pub mod contract;`）。选 core 而不是新建 `crates/ipc-contract`：`aaxsyspulse-core` **零依赖**，引导按 path 依赖它不会把主程序的 windows 0.58 拉进本次编译（引导用 0.61），也不用动 workspace 成员表与三份 lock。
  模块内容 = 类名 2 + 消息号 11 + 名字/路径/注册表 20 + `CONFIG_VERSION` + 两个派生辅助：
  ```rust
  pub const OVERLAY_WINDOW_CLASS: &str = "AAXSysPulse_WndClass";
  pub const WM_RELOAD_CONFIG: u32 = WM_APP + 8;      // 0x8008
  pub const WM_QUICK_RESTART: u32 = WM_APP + 9;      // 0x8009
  pub const APP_TECH_NAME: &str = "AAXSysPulse";
  pub const APP_USER_NAME: &str = "AAX SysPulse";
  pub const APP_DATA_DIR_NAME: &str = "AAXSysPulseC";  // 尾 C = 历史包袱，见 §12
  pub const CONFIG_VERSION: u32 = 3;
  pub fn migration_marker_name() -> String { format!("config_migrated_v{CONFIG_VERSION}") }
  pub fn wide_of(s: &str) -> Vec<u16> { /* UTF-16 + 尾 NUL */ }
  ```
- **关键设计：`w!()` 必须删掉，而不是"加测试比对"**。`windows::core::w!("…")` 要求**编译期字面量**，只要允许它存在，就永远存在"两份互不相干的字面量 + 一个只比较字面量副本的测试"这种假守卫。统一改为运行期转换：
  ```rust
  let class_w = aaxsyspulse_core::contract::wide_of(contract::OVERLAY_WINDOW_CLASS);
  let class_pcw = windows::core::PCWSTR(class_w.as_ptr());   // Vec 必须在 API 调用期间存活
  ```
  `RegisterClassExW` 把类名拷进原子表，故注册后即可丢 buffer；`CreateWindowExW`/`FindWindowW`/`PostMessageW` 是同步读取。`PCWSTR.0`/`as_ptr()` 在 windows 0.58 与 0.61 上同形，所以同一写法跨两侧可用。
- **接入点（实测引用数）**：主程序侧 `window.rs`（10 个 `WM_*` 全改为 `pub const X: u32 = contract::X`）、`tray.rs`、`settings/mod.rs`、`autostart.rs`、`config_io.rs`、`msr.rs`、`logging.rs`、`app/main.rs`、`app/pre_launch_checks.rs`、`win/examples/balloon_probe.rs`；引导侧 `notify.rs`、`lib.rs`、`process.rs`、`driver.rs`、`install.rs`（`use ... as c`，35 处）、`resources.rs`、`config.rs`、`shortcut.rs`、`guide_state.rs`。合计 65 处 `contract::` + 35 处 `c::` = **100 个引用点**。
- **`CONFIG_VERSION` 的"假唯一定义"**：`core/src/config.rs` 的同名 `pub const` 改为**再导出**（`pub use crate::contract::CONFIG_VERSION;`），既有约 10 处 `crate::config::CONFIG_VERSION` 引用零改动；引导 `config.rs` 新增 `pub const CONFIG_VERSION: u32 = contract::CONFIG_VERSION;`，并把 5 处 `version: 3,`、4 处 `unwrap_or(3)`、4 个 `save()` 裸串里的 `version = 3` 全部换成 `{ver}`（`ver = self.version` 作具名参数传入）。
  **这是一次行为变更（刻意）**：旧实现无论内存里是什么版本都写回 3；新实现回写自己的版本。配合主程序"磁盘版本 > `CONFIG_VERSION` ⇒ 不碰不降级"的规则，引导不再可能把新配置降级——这正是 `VersionSpanTooLarge` 破坏性弹窗的一条诱因。
- **未纳入契约的（刻意）**：`Local\AAXSysPulseGuide_SingleInstance` / `Local\AAXSysPulse_SingleInstance` 互斥体名（各自唯一所有者，跨进程不需要相等）、i18n 显示文案、`pre_launch_checks.rs` 两处英文弹窗正文、INI 头部注释串（见 §11-5 的普查）。
- **验收（实测）**：`grep -rn "AAXSysPulse_WndClass" sysoverlay/crates guide-app/src-tauri/src` → **1 行**，且正是 `contract.rs:25` 的定义本身；`grep -rn "0x800" guide-app/src-tauri/src` → 3 行，全部是 `notify.rs` 的**文档注释**，无代码字面量。

## 2. 1.2.1 类名副本 + `FindWindowW` 前缀误匹配

- **症状**：类名在 `window.rs`（3 处：注册、创建、查找）、`notify.rs`、`guide lib.rs:345`、`process.rs:22` 各写一份。报告记为"4 份"，实测口径不同但结论一致（见 §11-1）。
- **顺带发现的第二个缺陷（本批新增，报告未记）**：`find_overlay_hwnd` 的比较器把窗口类名与常量做 `zip` 逐字符比较 —— `zip` 以**较短的一方**收尾，因此 `AAXSysPulse_WndClassXyz` 会被判为匹配。任何进程注册一个以我们类名为前缀的窗口类，就能把 `WM_RELOAD_CONFIG`/`WM_QUICK_RESTART` 从真正的悬浮窗手里**劫走**。
- **如何修正**：`sysoverlay/crates/win/src/window.rs`
  ```rust
  let class_name = aaxsyspulse_core::contract::OVERLAY_WINDOW_CLASS;
  // ...EnumWindows 回调内
  if len as usize != class_name.len() { return false }          // 新增：长度相等
  buf[..len].iter().zip(class_name.encode_utf16())
     .all(|(a, b)| (*a as u8).to_ascii_lowercase() == (b as u8).to_ascii_lowercase())
  ```
  大小写不敏感是 Win32 原子表语义（类名查找不分大小写）；ASCII 前提由契约测试 `names_are_ascii_for_lossless_wide_literals` 钉住（13 个名字），所以 `as u8` 截断不会把非 ASCII 字符折叠成假相等。注册/创建两点同样改为 `wide_of` + `PCWSTR`。
- **为什么不能保留 `w!()`**：见 §1 第二条；`g!` 侧的 `PCWSTR` 常量一旦来自 `w!`，编译器就无法发现另一端漂移。
- **验收**：`grep` 同 §1；且注册点与查找点读同一个 `contract::OVERLAY_WINDOW_CLASS`（人工可读代码确认）。

## 5. P1-14 `RING0_TORN`：会话内不热恢复这条边界必须可见

- **报告原方案**："会话内清 torn 位 + 可见提示"。**只做了后半段，并换了一条更强的路**（见下）。
- **为什么要谨慎**：`RING0_TORN` 一旦置位（功耗行关闭触发 `teardown`：关句柄 + `ControlService(STOP)` 卸载内核驱动），本会话内所有 MSR 访问短路返回 `None`。清 torn 位等于在**同一个进程生命周期内重新 `StartService` 一个刚被我们停掉的内核驱动**——句柄所有权、`MsrPower` 的能量基线、工作线程（§6 的 `msr-worker`）都按"本会话不再有功耗"设计，热恢复要么把三处状态重写成可重入，要么留下 use-after-close 面。权衡后本批不动 `RING0_TORN`。
- **报告前提证伪（§11-3）**："驱动装好后引导能重装吗，还是必须重启"这一条里，**"缺驱动"这一半本来就能自愈**：`ring0()` 仅在 `RING0_TORN` 时短路；否则 `g.is_none() || RING0_STALE` 就会重跑 `open_ring0()`，即每轮采样都在重试。真正需要重启的只有"本会话 teardown 过"这一种。
- **如何修正（可见性 + 真正的修复通道）**：
  1. **引导侧补发快速重启**（`guide-app/src-tauri/src/lib.rs:232-246`）：`install_run` 成功后，`Repair` 与 `DriverOnly` 两条路径不会走到「完成引导」，过去**从不通知主程序**，于是主程序继续用旧驱动/旧句柄 ⇒ 用户反复重试无效。现补：
     ```rust
     if matches!(mode, InstallMode::Repair | InstallMode::DriverOnly) {
         notify::notify_main_quick_restart();               // WM_QUICK_RESTART 0x8009
         install::log_install("通知主程序重启", "成功", Some("修复/驱动重试后请求快速重启，以加载新驱动"));
     }
     ```
     `Full` 模式不发：首次安装必过引导流程，由 `guide_finish` 统一重启，发两次会打断用户。主程序未运行时 `deliver()` 静默返回（`FindWindowW` 失败即 no-op），不产生误报。
  2. **主程序侧的既有可见提示保留并接上契约**：`settings/mod.rs:909 show_teardown_notice()` 在功耗行关闭（以及 GPU/Util 三者全关）时弹原生提示告知"重启应用恢复"，标题改用 `contract::APP_TECH_NAME`（原为手抄 `"AAXSysPulse\0"`）。
  3. `RING0_TORN` 的语义在 `msr.rs:87`、`teardown()` 文档、`sampler.rs:96-98` 三处注释里统一写清"一次性、本会话不热恢复、重启恢复"，替换原先含糊的表述。
- **验收**：修好后安装日志出现「通知主程序重启」，主程序窗口消失并立即重现（交用户复核）。

## 6. P1-15 MSR 执行隔离：`MsrPowerAsync` + 超时上限

- **症状**：`MsrPower::sample` 底层是同步阻塞 `DeviceIoControl`，与 CPU/内存/GPU/网络跑在同一条采样线程上；设备无响应（驱动卡死、电源状态切换瞬间设备栈抖动）时**五个源一起定格**，而渲染看门狗只管渲染线程，对卡住的采样线程无所作为。
- **如何修正**：`sysoverlay/crates/win/src/msr.rs:636-806`（新增段）——阻塞调用挪到专用线程 `msr-power`，采样线程只 `recv_timeout`：
  ```rust
  pub struct MsrPowerAsync { req_tx, reply_rx, in_flight: bool, timeouts: u32, disabled: bool }
  pub fn sample(&mut self, now_ms: u64, timeout_ms: u64) -> Option<MsrFrame>   // 承诺：不阻塞超过 timeout_ms
  ```
  四条规则：① 超时 ⇒ 本帧功耗 `None`（行显示 `--`），其余四源照常更新；② `in_flight` 时**不重复派单**（否则每轮超时泄漏一条线程），迟到回包用 `try_recv` 收下并复位；③ 派单前 `while rx.try_recv().is_ok() {}` 丢弃迟到包，避免把上一轮的能量窗口当新值；④ 连续 `MSR_TIMEOUT_GIVEUP = 3` 次真实超时 ⇒ `disable()`：丢弃请求通道、本会话停止功耗采样（工作线程从卡住的调用返回后发现通道已死而自行退出，不留驻留线程）。线程创建失败同样 `disable`，不静默。
  `MsrFrame { watts, dram_available }`：Intel DRAM 域可用性必须随读数回传，否则 `SystemPower` 的"内存条 ×5W 去重"判据在隔离后拿不到。
- **连带修正**：`teardown()` 里对 `RING0` 的 `lock()` 改为 **`try_lock()`**（`msr.rs:402-407`）——工作线程卡死时正持有该锁，阻塞等待会把采样线程挂回**同一个死点**，"隔离"就退化成没做。取不到锁时只跳过显式关闭；那次阻塞调用返回后 `Ring0: Drop` 仍会 `CloseHandle`（§无：`Drop` 早先批次已加）。
- **消费侧**：`power_system.rs:94` 改为 `self.msr.sample(now_ms, timeout_ms)?`，超时语义天然落到既有 `Unavailable` 分支，UI 无需新状态。
- **验收**：`power_interval_ms ≥ 10 s` 时功耗行显示 `--` 而其余行照常跳动（交用户复核，§13-6）；正常机器上表现与批次 3 一致。

## 8. P2-12 释放的判据与原子性

- **症状**：`release_main_program` 旧判据是 `metadata.len() == bytes.len()` 即跳过。链接器产物"同尺寸不同内容"是常态（改字符串常量、版本号长度不变），半写失败的截断文件也可能凑出同样大小 ⇒ 经典故障"**安装完成但 exe 没变**"。写入是 `fs::write` 直写目标，失败即留半成品。
- **如何修正**：`guide-app/src-tauri/src/install.rs:30-115`
  - `fnv1a64(bytes)`：FNV-1a 64 位，**不引新依赖**；只在"大小已相同"这条少见的分支上才对既有文件算，代价可控（40 MB 百毫秒级）；
  - `same_content(path, bytes)`：先比大小再比指纹，逐字节等价才判"已是最新"；
  - `atomic_replace(temp, target, bytes)`：`fs::write(temp)` → `fs::rename(temp, target)` → `verify_file`。rename 失败映射为**专用错误** `InstallError::Locked`（`raw_os_error` 5/32 = `ERROR_ACCESS_DENIED`/`ERROR_SHARING_VIOLATION`，即主程序正在运行），提示语直接给动作："退出正在运行的主程序后重试"，而不是笼统 IO 错误；
  - 校验失败的清理：rename 成功后 temp 已不存在，半成品就是 `target` ⇒ 删掉 `target`（本批最后一步微调，注释写明原因），免得安装中止后「已安装检测」把截断文件报成可用主程序。
- **与报告方案的偏差（显式）**：报告建议"哈希 manifest 文件"。本批未落 manifest，理由是：manifest 要覆盖的场景（磁盘上既有文件与内置资源比对）已由 `same_content` 直接读文件解决，多一个 `.manifest` 反而多一个"与真实文件不一致"的状态源。
- **验收**：改 `AAXSysPulse.exe` 资源内容而保持尺寸不变 ⇒ 安装日志该步必须是**成功**而非"跳过"（构造验证成本高于收益，记为人工可复核逻辑，未实测）。
