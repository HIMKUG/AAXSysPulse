## 1. P1-18 D2D 工厂改为线程级

- **症状**：高画质引擎的 `ID2D1Factory` 存在进程级 `OnceLock` 里，而创建时用的类型是 `D2D1_FACTORY_TYPE_SINGLE_THREADED`。
- **根因**：`SINGLE_THREADED` 的契约是"工厂及其派生对象只能在创建它的那个线程上使用"。渲染线程一旦被看门狗 respawn（`gdi.rs` 的两条路径），新线程拿到的仍是**旧线程**创建的工厂 → 跨线程使用 = UB（轻则 `E_POINTER`/设备丢失，重则卡死，且卡死又触发 respawn，正反馈）。`dwrite_factory()` 用 `DWRITE_FACTORY_TYPE_SHARED`，本来就允许多线程，所以它**故意**保留 `OnceLock` —— 两者不是不一致，是契约不同。
- **如何修正**：`sysoverlay/crates/win/src/render_d2d.rs:66`
  ```rust
  fn d2d_factory() -> Option<ID2D1Factory> {
      thread_local! {
          static F: OnceCell<Option<ID2D1Factory>> = const { OnceCell::new() };
      }
      F.with(|f| {
          f.get_or_init(|| unsafe { D2D1CreateFactory(D2D1_FACTORY_TYPE_SINGLE_THREADED, None).ok() })
              .clone()
      })
  }
  ```
  用 `OnceCell<Option<..>>`（不是 `Option<OnceCell<..>>`）：`D2D1CreateFactory` 失败也要把"已试过且失败"钉住，避免每帧重试创建工厂。唯一调用方 `get_or_create_rt`（`let d2d = d2d_factory()?;`）不改，语义从"借引用"变成"拿本线程自己的 owned COM 句柄"。
- **为什么 `OnceLock` 版本编译得过但仍是错的**：类型系统不编码 COM 套间/线程亲和性，这类缺陷只在"线程换过"之后显形 —— 也就是只有 respawn 路径触发，日常跑不出来。
- **验收**：工厂创建点与消费点在同一函数族内且都走 `thread_local!`；`grep "static.*OnceLock<ID2D1Factory"` 无残留。

## 2. P1-17 respawn 预算统一 + 上线 spawn 失败不再静默

- **症状**：`frame wedge`（5s 无帧）路径有 `< 3` 的内联上限，`epoch stall`（30s 无新数据）路径**完全没有上限**；每次 respawn 都泄漏一个可能仍卡死的旧渲染线程。另外 `start()` 里 `let _ = spawn(...)`，线程创建失败时通道已关闭而无人知晓。
- **如何修正**：`sysoverlay/crates/win/src/gdi.rs:325-341`
  ```rust
  const RESPAWN_BUDGET: u32 = 3;
  fn take_respawn_budget(reason: &str) -> bool {
      let n = RESPAWN_COUNT.fetch_add(1, AtomicOrdering::Relaxed);
      if n < RESPAWN_BUDGET { return true; }
      RESPAWN_COUNT.fetch_sub(1, AtomicOrdering::Relaxed);   // 用尽后不再累计
      if !RESPAWN_GAVE_UP.swap(true, AtomicOrdering::Relaxed) {
          crate::probe::log(&format!("render watchdog: respawn cap ({RESPAWN_BUDGET}) reached ({reason}) — 不再新建渲染线程，保持当前渲染后端"));
      }
      false
  }
  ```
  两条路径改为共用它：`gdi.rs:437`（`if take_respawn_budget("frame wedge") { return WatchdogAction::Respawn; }`，旧的 `< 3` 与其独立日志行删除）、`gdi.rs:481`（`if take_respawn_budget("epoch stall") { Respawn } else { None }`）。
  `sysoverlay/crates/win/src/render_thread.rs:55/91`：`let _ =` 改成保留 `spawn_result`，失败时写诊断日志并把 `RENDER_TX` 置 `None`（`request()` 已容忍 `None`：`send_ok=false` → 复位 `RENDER_QUEUED`，不会自旋）。
- **与报告方案的偏差（刻意，改动最小）**：报告提过新增 `WatchdogAction::GiveUp` 并 `SW_HIDE`。本批只做"预算用尽 → `None` + 一次日志"，不隐藏窗口：隐藏会让用户以为程序崩了，且引入新的可见副作用。stall 路径也**不**顺带禁用 D2D（那是 `DisableD2d` 分支的职责，混在一起会让归因失效）。
- **3 的来历**：见 `gdi.rs:318-324` 注释 —— 与 `render_thread` 的线程数无关于"最多容忍几次卡死"，实测一次程序生命周期内未见过 2 次以上；两条路径必须共用同一个计数，否则各自 3 次 = 6 个泄漏线程。
- **验收**：`grep "RESPAWN_COUNT" gdi.rs` 只在 `take_respawn_budget` 内被读写；无第二处内联阈值。

## 3. P1-13 服务归属守卫（本批风险最高的一项）

- **症状**：`register_driver_service` 只 `CreateServiceW`，`stop_old_service`/`delete_old_service`/`start_driver_service` 拿到服务句柄就动手；`delete_old_service` 里的 `DeleteService` **不比对 `BinaryPath`** —— 若机器上存在别人注册的同名服务 `AAXSysPulseWinRing0`（指向任意二进制），本软件会把它删掉。反向问题同样存在：`get_driver_status` 只看"服务在不在 + 能不能开设备"，别人的同名服务会让 `driver_ok=true`，即**静默复用他人的内核驱动**（审查项 5.2.3）。
- **如何修正**：`guide-app/src-tauri/src/driver.rs`
  - 新增错误变体 `DriverError::ForeignService`（`#[error("检测到同名服务但不属于本软件，已停止对其做任何操作")]`，`:43`）；
  - `unsafe fn service_binary_path(svc) -> Option<String>`（`:139`）：`QueryServiceConfigW` 两段式调用（先 `None` 探长度，再 `Some(cfg)` 取值），取 `lpBinaryPathName`。windows 0.61 签名要点：`QueryServiceConfigW(h: SC_HANDLE, Option<*mut QUERY_SERVICE_CONFIGW>, buf_len: u32, *mut u32) -> windows_core::Result<()>`；`PWSTR(pub *mut u16)` → 用 `PCWSTR(lp.0 as *const u16).to_string()`。
  - `fn is_our_driver_binary(path: Option<&str>) -> bool`（`:164`）：`/`→`\`、整体小写，要求**目录前缀 = `DRIVER_TARGET_DIR`** 且**文件名 = `winring0x64.sys`**。两个条件都要：只比文件名则任何目录的 WinRing0 都能过；只比目录则别人往我们目录塞一个 `.sys` 也能过。
  - `unsafe fn ensure_ours(svc) -> Result<(), DriverError>`（`:173`）：不匹配则 `tracing::warn!`（带 `redact` 前的原始路径，便于本机排障）+ `Err(ForeignService)`。
  - 挂到四个动线上：`stop_old_service`（`stop_service` 之前）、`delete_old_service`（**`DeleteService` 之前**，全项目最危险的一行）、`start_driver_service`（`StartServiceW` 之前）、`get_driver_status`（`:456` 附近，`installed = ours`、`running = ours && …`）；`register_driver_service` 把 `HRESULT::from(WIN32_ERROR(1073 /*ERROR_SERVICE_EXISTS*/))` 映射成 `ForeignService`（`:338-341`）而不是笼统的 SCM 错误。
  - 新增单测 `#[cfg(all(test, windows))] mod ownership_tests`：`our_dir_and_file_counts_as_ours`（大小写混写、正斜杠都算我们的）、`anything_else_is_not_ours`（`kbdclass.sys`、其他目录、其他文件名、`None`、`Some("")`）。
- **界面无需新增元素（设计要点）**：拒绝 ⇒ 该步记 跳过/失败 ⇒ `get_driver_status` 报 `installed=false` ⇒ `driver_ok=false` ⇒ 走既有的第八部分「功耗监控不可用」分支。安全拒绝因此**天然可见**，不需要新 UI，也不会假装成功。
- **验收**：先手工注册一个同名、`BinaryPath` 指向 `C:\Windows\System32\drivers\kbdclass.sys` 的服务，再跑安装 ⇒ 必须报错退出且 `kbdclass.sys` 的服务仍在（`sc query` 可查）。

## 4. P2-15 页号硬校验 + 拒绝理由必须说出口

- **症状**：`goTo()` 的返回值与 `nextTarget()/prevTarget()` 的 `null` 全面无人处理：越界页号、不在当前路线的页、安装进行中离开第 3 页，三种情况都是"点下去什么都没发生，也没人解释"。
- **根因**：`goTo` 用写死的 `page > 14` 做合法性判断，而"存在 14 页"与"当前路线只有 N 页"是两件事；`next()`/`prev()` 拿到 `null` 直接 `return`。
- **如何修正**：`guide-app/src/wizard/composables/useGuide.js`
  - `:45` `const LAST_PAGE = Math.max(...PRESET_FLOW, ...CUSTOM_FLOW)` —— 上界由两条流程反推，新增页面不用再改校验；
  - `:416` `goTo` 开头 `if (!Number.isInteger(page) || page < 1 || page > LAST_PAGE) { log.error(...); notify('内部错误：目标页面不存在，已停在当前页。', 'error'); return false }`（`Number.isInteger` 同时挡住 `NaN`/字符串/小数）；
  - 安装进行中的拒绝加 `notify('安装正在进行中，请等它结束或点「退出安装」。', 'warn')`；"这一步不在当前引导路线里"的拒绝加 `notify('这一步不在当前引导路线里，已停在当前页。', 'warn')`；
  - `next()`/`prev()` 目标为 `null` 时不再静默：分别提示「已经是最后一步了。」「已经回到第一步了。」。
  - 复用的现成设施：`notify(text, type='warn', ttl=6000)`（`:147`）、`log = {info,warn,error}`（`:346`）—— 不新造提示通道。
- **验收**：控制台 `goTo(99)` / `goTo('4')` / `goTo(NaN)` 均不改变 `state.page` 且弹出一条 error toast（交用户复核）。

## 5. P2-10 取色器 Esc 取消后必须回同步

- **症状**：`<input type="color">` 里按住拖选实时预览，按 Esc 取消时浏览器把控件值**回滚**到打开前的颜色，但 `v-model`/`:value` 是单向绑定（状态本身没变）⇒ 不会重新派发 ⇒ 与 `state.colors` 失同步。表现：颜色选择器里显示 A、实际生效是 B。
- **如何修正**：`guide-app/src/wizard/pages/Page09Color.vue:54/76/99/103` 四处统一加 `@cancel="e => (e.target.value = <当前权威值>)"`（`state.colors.name` / `state.colors.value` / `colorOf(it.key,'name')` / `colorOf(it.key,'value')`），并在 `colorOf` 上方补一段事件语义注释：`input` 拖选中持续触发、`change` 只在取色器关闭时触发一次、`cancel` 是 Esc/关闭不采纳。
- **写入路径不变**：状态与落盘仍然只有 `setColor`/`setPerColor` → `notifyConfig` 一条路，取消路径**不**写状态（这正是"预览即状态"的反面，避免 Esc 也留痕）。
- **验收**：改色→拖选中→按 Esc → 控件与预览/落盘一致（交用户复核）。

## 7. P2-3 安装日志的会话边界与总结行

- **症状**：34 处 `log_install` 调用平铺在同一个文件里，既没有"这一次安装从哪开始"的分隔，也没有"成功几步/跳过几步/哪一步最终失败"的结论行；时间戳只有秒级。排障时要靠肉眼找边界。
- **如何修正**：`guide-app/src-tauri/src/install.rs:238/252`
  - `begin_install_session(label, mode)`：清零 `STEP_OK/STEP_SKIP/STEP_FAIL` 三个 `AtomicUsize`，写 `──────── {label} ────────` + `mode=… version=…`；

- **验收**：一次安装的 `install.log` 恰好有一头一尾两行、中间 9+ 步逐条；尾部三项之和 = 该会话的步数。

## 8. P2-14 魔法数字补来源

- **`Trends::CAP = 120`**（`sysoverlay/crates/core/src/history.rs:93-105`）：注释改为写清三件事 —— 语义是"保留最近 `CAP` 个**提交点**"而非"120 秒"；换算 `CAP × interval_ms`（档位 100/200/1000/2000/5000 ms）⇒ 窗口在 12 秒～600 秒之间浮动，默认 1000 ms 时才是 120 秒；内存代价 `4×120×4B`。
- **D2D 失败阈值**（`sysoverlay/crates/win/src/gdi.rs:534`）：裸 `if n >= 5` 提为 `const D2D_BIND_FAIL_THRESHOLD: u32 = 5;`，注释说明"这是经验值不是推导值"：单次失败极常见且本帧已由 GDI 兜底（用户无感），连续 5 帧（≈5 秒）仍失败才视为驱动/工厂级失效；并标注调大/调小各自的代价、以及 panic 分支不受此阈值影响。
- **两级防抖**（`guide-app/src/wizard/composables/useGuide.js:263` + `guide-app/src-tauri/src/notify.rs:32-41`）：JS 侧写死的 `100` 提为 `const DEBOUNCE = { backup: 100 }`；两处互相点名 —— `backup:100` 合并的是前端→后端的 `guide_backup` IPC，`DEBOUNCE_MS:50` 合并的是后端→主程序的 `WM_RELOAD_CONFIG` 投递（尾随防抖），并写明**两级叠加的最坏延迟 = 150ms**、改一边必须同步另一边。
- **`SESSION_CAP_BYTES = 8MB`** 原本就有注释，未动。
- **验收**：三处常量各自能回答"这个数怎么来的、改动会连带什么"。

## 9. P2-6 收尾：config.rs 的 3 条 dead-code

- **症状**：批次 2 之后 `cargo check` 仍剩 3 条警告，全在 `guide-app/src-tauri/src/config.rs` —— `ConfigError::Parse` 从不被构造、`AllConfigs` 结构体与其 `load`/`save` 零引用。
