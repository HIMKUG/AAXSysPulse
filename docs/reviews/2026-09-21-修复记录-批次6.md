## ② P1-21 边界：lint 口径集中声明（warn-only，不阻塞构建）

**报告前提**：是否引入 clippy 门禁（`let_underscore_must_use` / `unwrap_used`）是批次 5 §12
第 3 行的决策项；本批把"能零成本成立的部分"落地，把"不成立的部分"用实测数据交回决策。

**如何修正**：三层声明，全部**只声明口径、不改构建结果**。

1. 根 `Cargo.toml:21-30` 新增 `[workspace.lints.clippy]`，当前只有一条：
   `too_many_arguments = "allow"`，理由写在该表上方注释里。
   5 个成员 crate 各自新增顶层 `[lints]` + `workspace = true` 继承。
   - **踩过的坑**：先按 `[package] lints.workspace = true` 写 ⇒ cargo 报
     `unused manifest key: package.lints`（**静默不生效**）。`lints` 是**顶层表**，
     必须写成 `[lints]\nworkspace = true`。已用最小复现工程验证过差异。
     证据：错误写法时 `[lints]` 完全不生效，正确写法后 clippy 命令行里出现
     `--allow=clippy::too_many_arguments`。
2. 各 crate 根的 `#![cfg_attr(test, allow(clippy::field_reassign_with_default))]`
   —— `field_reassign` 的 allow **只在 test 编译时成立**，workspace 表表达不了 cfg，
   所以写在 crate 根：`core/src/lib.rs`、`ui/src/lib.rs`、`guide-app/src-tauri/src/lib.rs`。
3. 5 个 crate 根的 `#![cfg_attr(not(test), warn(clippy::unwrap_used))]`。

**实测（`unwrap_used` 试点的关键数据）**：`cargo clippy --workspace --lib --bins
-- -W clippy::unwrap_used` ⇒ **生产代码 0 处命中**（27 条命中全在 `#[cfg(test)]`，
其中 `ui/src/renderer/tests.rs` 8 条）。 ⇒ 这条门禁**今天就绿**，只挡未来回归，
成本 = 零噪声。同口径下 `expect_used` 5 条 / `panic` 3 条：5 条里 4 条在 `build.rs`
（构建脚本 panic = 构建失败，是**正确行为**），生产侧只剩 `guide lib.rs:960` 的
`Builder::run().expect(...)` ⇒ 本批**没有**启用这两条。

**偏差（显式标注）**：
- 报告设想的"门禁"通常指 **deny**；本批只到 **warn**，不阻塞任何构建 —— 升 deny 需用户点头。
- `let_underscore_must_use` **不可行**：强制打开后生产代码 234 处命中（全 target 273），
  集中在 `settings/mod.rs` 71、`config_io.rs` 53、`window.rs` 34、`titlebar.rs` 20。
  这条不是"改代码"能消的（绝大多数是**有意的** Win32 返回值丢弃），只能作定向审查 ⇒ 进 §11。

**验收**：`cargo clippy --workspace --all-targets`（touch 后全量重检）⇒ **0 条**；

## ④ P2-8：安装步骤心跳（长步骤不再"永远 running"）

**报告前提**：`install_run` 已逐步 `log_install` 落盘，但事件侧缺 `install-progress` 心跳 ⇒
慢步骤（驱动注册/启动服务）在界面上停着不动，用户以为卡死。

**实测**：
- 前端 `useGuide.js:816` 收到 `install-progress` 时**总是**用 `payload.text` 覆盖
  `state.install.text` 并对 `pct` 做 clamp ⇒ **复用同一事件即可，前端零改动**。
- `INVOKE_TIMEOUT_MS = 0`（invoke 无超时）⇒ 真卡住时前端确实只能永远显示 'running'。

**如何修正**（`guide-app/src-tauri/src/install.rs:383-441`）：
- `emit_progress`（`:443`）在每次追发进度时把 `(pct, text, Instant::now())` 记进
  `STEP_ANCHOR` —— 锚点由**真实步骤**拥有，心跳只读它。
- `Heartbeat::start(app)`：`HEARTBEAT_ON: AtomicBool` 的 `swap(true)` 保证全进程只有一条
  `install-heartbeat` 线程；线程每 500ms 读锚点，`pct >= 100` 不发（避免"安装完成"后又冒
  "已用 N 秒"），否则追发 `text = "{text}（已用 {secs} 秒）"`，`pct` 原样重复。
- `run_install` 在 `begin_install_session(...)` 之后 `let _heartbeat = Heartbeat::start(app);`
  ⇒ 随作用域退出 `Drop` 复位开关（`DriverOnly` / `Repair` 两条入口共用同一函数，自动覆盖）。
- 锁中毒用 `STEP_ANCHOR.lock().unwrap_or_else(|e| e.into_inner())`，不用 `unwrap()` ⇒
  与 ② 的 `unwrap_used` 门禁口径一致。

**偏差**：报告设想的是"长步骤内部定期回报进度"；本批做法是**旁路线程复用锚点**，
不改任何一步的实现。百分比不会因此前进（步骤真卡住时百分比本就该停着），
前进的只有"已用 N 秒"这句人话。

**验收（需人工，见 §13）**：安装页第 35%/45%/55%/65%/75% 任一步骤停留 > 1s 时，
副标题应每 500ms 刷新秒数；到 100%「安装完成」后不得再出现"已用 N 秒"。
