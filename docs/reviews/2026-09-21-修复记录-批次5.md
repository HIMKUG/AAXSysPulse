## ① P1-20：引导启动期的日志 panic 降级为静默丢弃

**报告前提**：`lib.rs` 日志目录不可写 / 文件打不开 ⇒ `.expect("无法创建日志文件")`，
表现为"双击图标后什么都不发生"。

**实测**：`expect` 确实存在（旧 `:799` 附近），且位置在 `run()` 的**最前面**——
早于 `tauri::Builder`，因此 panic 时既无窗口也无托盘，用户没有任何出口。

**如何修正**（`guide-app/src-tauri/src/lib.rs:916-932`）：
1. `EncryptedLogFile::file` 由 `std::fs::File` 改为 `Option<std::fs::File>`（`:868`）；
2. `OpenOptions::new()...open(&log_path).ok()` 不再 panic；起始偏移从
   `metadata().len()` 取，取不到则 0（`:923-927`）；
3. `write`/`flush` 里 `if let Some(file) = inner.file.as_mut()` 才落盘，
   **偏移照常按 `buf.len()` 推进** ⇒ 即使某次写失败，密钥流与"逻辑文件偏移"仍一致；
   真正的错位风险只在读端（`decrypt_log()` 按整文件偏移解），所以这里宁可
   **丢日志也不制造错位**：写失败时整段丢弃而不是留下半截。
4. 结论写进结构体注释（`:865-867`）："为日志 panic 的表现是窗口根本不出现，
   比丢日志严重一个量级"。

**与报告方案的偏差**：报告建议"降级为 eprintln + 继续跑"。`eprintln` 在 GUI 子系统
（`windows_subsystem = "windows"`）里没有任何出口，故改为"注释里写明降级策略"，
不假装能提示用户。

**验收**：`cargo check` 通过；`config.rs` 无改动。人工构造只读目录成本高（需改
`%LOCALAPPDATA%` ACL），留给复核时顺手做。

## ② P1-20：`RING0` 互斥锁中毒不得成为二次故障源

**报告前提**：`msr.rs:332` 在**采样热路径**上 `RING0.lock().unwrap()`；std Mutex 中毒即
panic ⇒ 一次持锁 panic 后每轮采样都 panic（与 2.1.4 耦合）。

**如何修正**（`sysoverlay/crates/win/src/msr.rs`）：
- 新增 `fn lock_ring0() -> MutexGuard<'static, Option<Ring0>>`（`:344`），实现
  `self.lock().unwrap_or_else(|e| e.into_inner())`；`ring0()` 与相关路径统一走它。
  理由与 ① 同理：这条锁保护的是"驱动句柄镜像"，取回被 panic 抛下的值是**语义正确**的
  （句柄本身仍然有效），而让采样线程反复 panic 才是放大器。
- `teardown()` 保持批次 4 的 `RING0.try_lock()`（不与在途采样争锁）。
- 新增单测 `poisoned_ring0_lock_still_usable`（`:824`）：起线程持锁 panic 制造中毒 ⇒
  `catch_unwind` 内断言 `lock_ring0()` 仍可取到并 `take()`，最后 `RING0.clear_poison()`
  把状态还回去（否则同一测试二进制里后续测试踩到中毒锁，产生假红/假绿）。

## ⑤ P1-21 / 2.1.6：`RESUME_NOTIFY` 语义与 poke 留痕

**报告前提**：唤醒采样线程的通道是 `OnceLock<Sender>`，五处 `let _ = tx.send(())`
把返回值丢掉；通道正是"采样线程永不退出"这一隐含契约的**唯一观测点**。

**如何修正**（`sysoverlay/crates/win/src/window.rs`）：
1. 新增 `fn poke_sampler(reason: &str)`（`:581`）：`None` → 记"通道尚未建立"；
   `Some(tx)` 但 `send` 失败 → 记 `"{e} —— 采样线程已退出？最多晚 5 秒刷新"`。
2. 四处**本进程内**的 poke 全部改走它并带上调用点标签：
   `:857 fullscreen-restore` / `:939 tray-show` / `:1079 power-resume-automatic` /
   `:1109 session-unlock`。
3. **删掉第五处**（`handle_second_instance()`，`:1720`）：`RESUME_NOTIFY` 是模块静态
   `OnceLock`，第二实例进程里恒为 `None` ⇒ 那一行从来就是死代码（不是"偶发失败"）。
   注释里写明显示后的唤醒由采样线程**自身的 1 s 可见性重查**兜底
   （`app/src/main.rs:532-537` 的隐藏等待循环），代价是最多 1 s 延迟，不会漏刷新。
4. `setup_resume_channel()`（`:1474-1486`）从 `let _ = RESUME_NOTIFY.set(tx)` 改为
   `.set(tx).is_err()` 时记一条日志：重复 setup 意味着**新 receiver 永远收不到 poke**
   （poke 只会打到旧 Sender），必须让"线程重建"这件事在日志里可见。
5. 静态字段文档改写：`OnceLock` 只在**本进程**有效、隐含契约是"采样线程每轮
   `catch_unwind` 永不退出"、只有第一实例持通道（`:565-575`）。

**为什么只加日志、不加自愈**：采样线程的所有等待都有 `recv_timeout` 上界
（100 ms / 1 s / 5 s），所以"丢一次 poke"在语义上**只影响延迟不影响正确性**——
把 `OnceLock` 换成 `Mutex<Option<Sender>>` 去重建通道属过度设计（见 §11 勘误 21）。

## ⑥ P1-21 + 2.1.3：关键返回值的分层处理

报告把"所有 `let _ =` 都要判"当成一锅粥。本批按**后果**分三层处理：

**A 层：谎报成功（必须修）**
- `autostart_set`（`guide lib.rs:408-420`）旧顺序是**先** `sys.save()`（写
  `autostart = true`）**再** `let _ = RegSetValueExW(...)` ⇒ 注册表写失败时命令仍返回
  `Ok`，前端显示"已开启"，下次开机什么都没有。现改为：
  `set_autostart_run_key(enabled)`（`:425-479`）**先做 OS 侧、成功后才落盘**，
  失败映射成 `GuideError("AUTOSTART_WRITE_FAILED")`（前端已有 toast 出口）。
  顺带处理 windows 0.61 的签名事实：`RegSetValueExW`/`RegDeleteValueW` 返回
  `WIN32_ERROR` 而非 `Result`，删值时 `ERROR_FILE_NOT_FOUND` 视为已关闭（不是错误）。
- `guide_finish`（`:683-706`）：`let _ = state.save()` ⇒ 引导"完成"后下次启动仍弹
  "继续上次引导"；`let _ = create_desktop_shortcut()` ⇒ 用户勾了"创建桌面快捷方式"
  而什么都没发生。现在两者都进 `install::log_install(...)` 的成功/失败计数
  （不阻断完成流程：配置本身已写盘成功，为标记文件失败把用户卡在最后一步更糟）。

**B 层：唯一报警器被拆掉（必须修）**
- `gdi::request_render`（`win/src/gdi.rs:532-551`）：`RENDER_EPOCH` 先自增、随后
  `let _ = PostMessageW(hwnd, WM_NEW_SNAPSHOT, ...)` ⇒ "标记为已请求但没人被叫醒"，
  最坏等 30 s 纪元判据 respawn。现在判返回值，失败时调
  `render_thread::note_wake_lost()`（`render_thread.rs:192`，新增 `pub(crate)`）
  交还排队权 + 写探针日志 ⇒ 下一个请求即刻重试。
  **验收命令** `grep -n "let _ = PostMessage" sysoverlay/crates/win/src/gdi.rs` → 0 行（实测已为 0）。
- `mark_d2d_broken_and_persist_gdi`（`:608-626`）同族：`D2D_BROKEN` 原子标志已置，
  本会话禁 D2D 是生效的；投不出去只丢"持久化"，故**只记日志不重试**，
  注释写明"本会话已禁 D2D，但配置回退未落盘"。
- **UIPI 放行（补做，同一族）**：`window.rs:1610-1619` 的
  `ChangeWindowMessageFilterEx(hwnd, WM_RELOAD_CONFIG / WM_QUICK_RESTART, MSGFLT_ALLOW, None)`
  旧代码直接丢弃返回值。它正是"跨完整性投递"的开关：放行失败时引导侧的
  `PostMessageW` **仍然返回成功**（UIPI 静默丢弃 ⇒ 表现为"改了设置悬浮窗毫无反应"），
  两侧都不报错 ⇒ 与 B 层同族（唯一报警器被拆掉）。现在判 `Result`，
  `Err` 时 `probe::log("uipi: 消息 {msg:#x} 放行失败（{e}）—— 跨完整性投递将被静默丢弃")`。
  放行本身仍不做重试、不阻断启动：失败只意味着"跨完整性那条通路不可用"，
  同完整性（都提权 / 都不提权）下消息照常送达。

**C 层：丢弃是正确的（明确保留，不改）**
- `notify.rs::deliver()` 的 `PostMessageW` 已有 `tracing::warn!` + 3 次退避重试（批次 2 的 P1-10）。
