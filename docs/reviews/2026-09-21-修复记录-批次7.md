## ④ `history` 的两处错误心智模型（9.3）

- **报告前提**：`crates/win/src/history.rs:14` 写"采样线程每轮 push 一份最新点"。
- **实测**：`history::push` 的唯一调用点在 `if should_commit { … }` 里
  （`crates/app/src/main.rs:722-728`）⇒ **提交闸门放行才 push**，与采样轮次不是一回事。
  叠加 idle 闸门（8.27）时，"每轮"与真实时间的关系更弱。
- **第二处**：注释与批次 6 文档都假定存在一个"曲线窗口"来读这份 `Trends`。实测
  `win::history::get()` 与 `peek_seq()` **零调用方** —— 读取侧已从仓库移除，写侧还在跑。
- **如何修正**：两个文件的模块文档按上述事实重写，`get()`/`peek_seq()` 各加
  "⚠️ 当前零调用方"的逐项标注；`core::history::Trends::CAP` 的注释把"每轮采样"改成
  "每次提交闸门放行"，并保留批次 6 已经写进去的"x 轴必须按点数 × interval 推导"的警告。
- **不做的事**：不去"顺手把曲线窗口接回来" —— 那是 §11-3 的决策项，仍在等表态。

## ⑤ `notifyConfig` 取消整包兜底（3.2.1 / P1-8）

- **报告前提**：前端存在"没有显式 patch 就写整包 `snapshot()`"的兜底路径。
- **为什么危险（本批实测后端语义）**：`config_patch` 的两个键在值为 `null` 时的口径是
  **全部复位**，不是"不动" ——
  `guide src-tauri/src/config.rs:709`（`per_item_colors: null` ⇒ 清逐项配色）、
  `:802`（`per_item_name_mode: null` ⇒ 每一项 `short = 0`）。
  所以一次"只是想落个别的字段"的整包写入，会把用户手工调过的逐项配色/逐项名称模式
  一起抹平。
- **如何修正**：`notifyConfig(patch)` 收到非对象直接 `log.error` + 返回，**不再兜底**。
  调用方必须显式说要写哪些键。
- **偏差**：没去动 `saveConfig()` / `guide_save_config` 这条整包写盘路线 —— 它属 P1-3
  的决策范围（等用户表态），本批只把"隐式整包"这一条口子关掉。
- **验收**：`grep -n 'snapshot()' useGuide.js` 里 `notifyConfig` 函数体内不再出现。

## ⑪ `app` crate 单测 + `date_to_ms` 形状闸门（P2-13 收尾）

- **报告前提**：P2-13 的尾巴记着"`crates/app` 零测试"。
- **如何修正（测试）**：给 `pre_launch_checks.rs` 的四个纯函数补 8 条单测，全部不碰
  弹窗 / SCM / 真驱动：
  `is_leap_year` 的格里高利四百年表；`date_to_ms` 的三个**写死的纪元锚点**
  （19700101→0、20240101→1704067200000、20260101→1767225600000）；
  跨月/跨年/闰秒边界的"正好差一天"；坏值集合；`time_since(u64::MAX) == 0`
  （把"`date==0` ⇒ `u64::MAX` ⇒ 差值 0 ⇒ 未满一周，真正让首弹成立的是调用点那条
  `last_date == 0 ||` 短路"这个**两条才成立**的隐含契约钉住）；
  `current_date()` 的形状合法性；`current_date()` 与 `date_to_ms` 两条独立实现互相吻合
  （今天的 UTC 0 点 ≤ now < +1 天）；时钟被往回调时 `saturating_sub` 必须给 0。
- **顺手修真崩溃**（写这批测试逼出来的，不在候选清单）：
  - `date_to_ms` 原先假定入参一定是合法 YYYYMMDD，但 `*_check_last_date` 是从
    `system.cfg` 直接 `parse_u32` 出来的**自由 u32**（`core/src/config/system.rs:218`）。
    手改或半写坏的文件给 `4294967295` ⇒ `month = 72` ⇒ `days_in_months[m - 1]` **越界 panic**；
    `day = 0` ⇒ `day - 1` 在 debug/测试构建下**下溢 panic**。
  - 位置要命：它在 `run_pre_launch_checks` 里跑，**早于窗口创建** ⇒ 用户侧表现是
    "双击 exe 毫无反应，任务管理器里进程一闪就没"，而且没有任何日志（弹窗都没走到）。
  - 修正：形状闸门 —— 年不在 `1970..=9999`、月不在 `1..=12`、日为 0，一律返回
    `u64::MAX`（= "从未检查过"，与 `date == 0` 同语义）。**宁多弹一次也不崩**，
    且不改任何正常路径的行为。
- **顺路清掉的两处"说明与实现不符"**（同 ① 的性质）：
  - `crates/app/src/lib.rs` 整文件只有一句 `// Placeholder: App implementation in 2B agent.`
    ⇒ 改为说明"lib 目标为空且刻意，全部代码在 bin 目标 `main.rs`，模块由 `main.rs` 挂载"，
    并警告"真要挪进 lib 时得同步删 `main.rs` 的 `mod`，否则两份定义打架"。
  - `crates/app/src/driver_installer.rs` **没有任何地方 `mod` 它**（`crates/app` 里唯一的
    模块声明是 `main.rs:29 mod pre_launch_checks;`，`Cargo.toml` 只声明一个 `[[bin]]`）
    ⇒ 与 9.5 的 `watcher.rs` 完全同形。本批**只在文件头加了死代码标注**，没删（进 §11 决策）。
