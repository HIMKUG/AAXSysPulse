## 1. capability 窗口 label 与真实窗口不一致（P0-1，出处 9.15 / 8B.A）

- **症状**：正式包（非 dev）里安装页进度永久停在 0%，`install-progress` / `install-done` 一条都收不到，且完成按钮不出现；开发态（浏览器）完全不复现。
- **根因**：Tauri v2 的事件 ACL 按**窗口 label** 判定。`capabilities/default.json` 声明的是 `"windows": ["main"]`，而 `tauri.conf.json:15` 的真实 label 是 `"guide"` → 该 label 上 `listen()` 被 ACL 拒绝，返回 rejected Promise。
- **如何修正**：`guide-app/src-tauri/capabilities/default.json:5` 改为 `"windows": ["guide"]`，并把 `description` 写明"label 必须与 `tauri.conf.json app.windows[0].label` 一致"，避免下次改窗口名时又对不上。
- **连带修正**：见第 2 项 —— 只有 label 修好还不够，`listen()` 的拒绝过去被完全吞掉，同类问题下次仍然零提示。

- **症状**：`release_main_program` **恒被跳过** → 安装流程走完但磁盘上没有主程序 exe，用户看到"安装完成但没反应"。

## 4. 单实例互斥体从"假的"改成真的（P0-12，出处 8B.F）

- **症状**：两个引导可同时启动，并发改服务、并发改写同一批 INI（配合 P0-11 的无幂等，没有任何屏障）。
- **根因**（三层）：
  1. `CreateMutexW` 成功后立刻 `CloseHandle` —— 命名互斥体是引用计数的，最后一个引用消失即销毁内核对象，`ERROR_ALREADY_EXISTS` 永远不可能出现；
  2. 名字用了 `Global\` 前缀，标准用户没有 `SeCreateGlobalPrivilege`，`CreateMutexW` 直接 `ACCESS_DENIED`；
  3. 同一件事在三处各写一份：`process.rs::is_guide_already_running`、`lib.rs::is_guide_already_running_inner`、`lib.rs` 顶部的 `GUIDE_MUTEX_CREATED: Lazy<Mutex<bool>>`，且 `driver.rs` 里还有一个空函数 `close_guide_mutex()`。
- **如何修正**：
  - `process.rs:13-18` 名字改为 `Local\AAXSysPulseGuide_SingleInstance`（会话局部，不需要特权；引导也不需要跨会话单实例），注释写明理由。
  - `process.rs:33-68` `acquire_guide_single_instance()`：成功时把句柄数值存入 `GUIDE_MUTEX_HANDLE: AtomicUsize`（`process.rs:10`）并**不** `CloseHandle`，靠进程退出释放；`ERROR_ALREADY_EXISTS` 时才关掉自己这一份引用并返回 `false`；`CreateMutexW` 本身失败（极端环境）时**放行 + `tracing::warn!`**，不让单实例保护变成启动障碍。
  - `process.rs:70-89` 新增 `release_guide_single_instance()`；`process.rs:91`/`lib.rs` 的 `not(windows)` 分支各留一个空实现。
  - `driver.rs:369-381`（提权重启）：在 `ShellExecuteW(runas)` **之前**显式 `release_guide_single_instance()`。这是"长期持有句柄"带来的唯一新风险：提权后的新实例与本实例在**同一会话**（共享 `Local\`），而 `ShellExecuteW` 会阻塞到 UAC 交互结束，新实例几乎必然先于本实例 `exit(0)` 启动 —— 不释放就会出现"点了提权，两个窗口都没了"。
  - 删除 `lib.rs` 的 `is_guide_already_running_inner()`、`GUIDE_MUTEX_CREATED` 静态、`once_cell::sync::Lazy` 导入，以及 `setup()` 里那段 `emit("guide:force-quit")`（该事件前端从未监听，见 8B.F/8B.B）；`run()` 现在只在 `--autostart` 分支之后做一次 `if !acquire_guide_single_instance() { exit(1) }`（`lib.rs:805`）。
  - 删除 `driver.rs` 的空函数 `close_guide_mutex()` 及其调用。

## 5. 配置文件原子写：去掉"先删后改"的窗口（P1-1，出处 1.1.1 / 8.2）

- **症状**：主程序偶发读到"配置缺失"→ 回落默认值 → 回写 → 整包个性化设置被默认值销毁。
- **根因**：`config.rs` 的 `atomic_write` 是 `写 .tmp → fs::remove_file(目标) → rename`。删与改名之间**目标文件不存在**；`.tmp` 名字还固定（`path.with_extension("tmp")`），两个写者并发会互相顶掉临时文件。
  （报告 P1-1 原文写成"`std::fs::write` 截断重写"，机制描述有误，见文末勘误。）
- **如何修正**（`guide-app/src-tauri/src/config.rs:1034-1085`）：
  - `temp_path_for()`：唯一临时名 `.<原名>.<pid>.<seq>.tmp`（`AtomicU32` 序号）。
  - `atomic_write()`：写 tmp → `sync_all()` → `fs::rename(tmp, target)`，**不再 `remove_file(target)`**。`std::fs::rename` 在 Windows 上就是 `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`，目标已存在甚至被别的进程共享打开时可直接替换，删除步骤本来就是多余的。
  - rename 退避重试 3 次（30/60/90 ms，覆盖主程序瞬时读盘占用），三次仍失败才清理 tmp 并返回错误 —— 不再假装成功。
  - 签名改成 `atomic_write<E: From<io::Error>>(...) -> Result<(), E>`，因此 `config.rs` 四处调用点（`:351/:480/:671/:929`）与 `guide_state.rs` 的尾表达式写法都无需改动。
  - `guide_state.rs` 删掉自己那份重复实现，改调 `crate::config::atomic_write`（并清掉随之无用的 `File` / `Write` 导入）。
- **验收**：安装/引导过程中反复改设置，`%APPDATA%\AAXSysPulseC\config\` 下任何时刻都不应出现"文件消失"的采样点；`*.tmp` 残留应随失败清理。

## 6. 配置变更通知改成尾随防抖 + 投递重试（P1-2 局部，出处 1.1.3 / 8.6）

- **症状**："改了设置但悬浮窗没反应"，且完全没有痕迹。
- **根因**：`notify.rs` 的 50 ms 防抖是**头部**防抖（窗口期内的后续调用直接丢弃）→ 恰恰可能丢掉**最后一次**改动；`PostMessageW` 返回值被 `let _ =` 吞掉；主程序窗口正在销毁/重启时投递失败无人知晓。
- **如何修正**（`guide-app/src-tauri/src/notify.rs` 全文件重写，105 行）：
  - 改为**尾随**防抖：调用即 `PENDING=true`；`FLUSHER_ARMED` 用 `swap` 保证只有一个短命线程在跑，每睡 `DEBOUNCE_MS` 检查并 `swap(false)` 取出 pending 后投递，`PENDING` 再次为空才解除 armed 并退出（不会遗留常驻线程，也不会无限循环）。
  - 新增 `deliver(msg) -> bool`：`FindWindowW` 未命中 → 返回 false（主程序没在跑，不是错误）；`PostMessageW` 返回 `Err` → `tracing::warn!` 并按 20/40/60 ms 退避，最多 3 次。
  - `notify_main_quick_restart()` 先冲掉 pending 的 reload 通知再发 `WM_QUICK_RESTART`，避免"重启新实例、旧实例还没落盘最后一次改动"。
  - 旧的 `LAST_NOTIFY_MS: AtomicU64` + 系统时间比较整个去掉（不需要时间戳，靠标志位与睡窗计时）。
- **仍属本面未修的**：主程序侧收到 `WM_RELOAD_CONFIG` 后**没有 ACK 通道**（报告 1.2.2 的"无确认"）。真正闭环需要双向消息或状态回读，属批次 3。

## 9. 悬浮窗屏幕外钳制（P1-7 主程序半边，出处 2.3.2 / 8.33 / 9.2）

- **症状**：窗口能被完全拖出所有显示器；拔掉副屏后重启，窗口落在屏外且**没有任何入口能救**（无任务栏、无标题栏）。原代码 `window.rs:614-616` 注释承诺"释放时统一做一次安全钳制"，但该钳制**从未存在**（§9 说明与实现不符条目）。
- **如何修正**（`sysoverlay/crates/win/src/window.rs`）：
  - 新增 `clamp_to_visible(x, y, w, h)`（`:1340`）：以 `MonitorFromPoint(窗口中心, MONITOR_DEFAULTTONEAREST)` 取"最近显示器"，用 `GetMonitorInfoW` 的 `rcMonitor` 把位置夹到"至少 `MIN_VISIBLE = 40` 像素在屏内"。

## 10. 引导日志：目录统一 + 密文/明文分治 + 密钥流对齐（P1-11，出处 7.3.1 / 7.1.5 / 8.4 / 9.13）

- **症状**：日志查看功能**恒空**（报告原话），而实际比"恒空"更糟：
  1. 写入方 `run()` 写 `%LOCALAPPDATA%\AAXSysPulse\logs`，读取方 `guide_view_logs` 读 `%LOCALAPPDATA%\AAXSysPulseC\logs`（多一个 `C`），目录里根本没有文件；
  2. `install.log` 是**明文**，查看器却对所有 `.log` 一律做 XOR 解密 → 即使改对目录，安装日志也是乱码；
  3. XOR 密钥流错位：写入端每次 `write()` 都从 `key[0]` 重新开始，读取端却按**整文件字节偏移**解密 → 除第一条记录外全部是乱码；
  4. 日志文件名用手工历法（`days/365` + 逐月减）算日期，`month_day[m]` 在误差下可越界 panic，且 `duration_since(..).unwrap()` 是启动路径上的 panic 面；
  5. tracing 的 `with_writer` 闭包**每条日志记录重开一次文件句柄**（`lib.rs` 旧 `:795`），并带 `expect`（报告 P1-20 点名的"每行日志重开文件 + expect"）。
- **如何修正**（`guide-app/src-tauri/src/lib.rs`）：
  - 新增 `guide_log_dir()`（`:674`）作为**唯一来源**，写入方与 `guide_view_logs` 都用它；注释写明"两处各写一份路径常量"正是本缺陷成因。
  - `guide_view_logs` 按文件名分治：`guide_*.log` 才 XOR 解密，其余（`install.log`）按明文读。
  - 写入端重写为 `EncryptedLogFile { file, key, pos }` + `EncryptedLogWriter(Arc<Mutex<..>>)`（`:729-777`）：密钥流按**文件绝对偏移**取值，与读取端严格对齐；"取偏移 + 落盘"在同一把锁内完成（`pos` 初值取已有长度，跨次启动追加仍然对齐），全进程只开**一个**句柄 —— 顺带消掉 P1-20 的每行重开 + `expect`。
  - 日期改用已在依赖里的 `chrono::Local::now().format("%Y-%m-%d")`，删除手工历法；`Box::leak` 出来的重复密钥字符串删除，统一用 `LOG_XOR_KEY` 常量（写读两端共用同一份定义）。
- **仍未修（下一批）**：日志无体积上限/无跨会话清理（P2-2）、"加密"其实只是 XOR 混淆（说明文档口径需改，见 §9.13）。

## 报告勘误（写代码时发现，已核实）

1. **P1-1 机制描述错误**：报告写"引导 `config_patch` 用 `std::fs::write` 截断重写"。真实代码是 `atomic_write`（写 tmp + `remove_file(目标)` + `rename`），所以缺陷不是"截断读到半截"，而是**删除与改名之间目标文件不存在**。修复方向不变（本批第 5 项），但影响窗口与判据描述以此为准。
2. **"主程序启动后不主动 reload 一次"这一条无需修**：`sysoverlay/crates/app/src/main.rs:202` 进入消息循环前已经无条件 `config_io::load_config()`。1.2.4 / 8.6 中据此提出的"补一次启动读盘"是空操作，结论应降级。
3. **前端路径前缀错误**：报告里 `guide-app/src/frontend/src/lib/bridge.js`、`.../frontend/src/wizard/...` 均不存在，真实前缀是 `guide-app/src/wizard/`（`bridge.js`、`composables/useGuide.js`、`GuideWizard.vue`、`pages/Page*.vue`、`vite.config.js`）。引用行号有效，前缀需按本条替换。
